看 agent 架构图时，经常会遇到一串名词：skills、mcp、tools、subagents、hooks、plugins。

单独查每个词，都能找到解释。但放到一张图里，又容易产生几个问题：

- 已经有工具了，为什么还需要 skill？
- mcp 和工具是一回事吗？
- 多一个 subagent，是不是就多了一个模型？
- 把规则写进文件，ai 就一定会遵守吗？

可以先记住这句话：

> **agent 负责推进任务，tools 负责具体操作，skills 提供做事方法，mcp 负责连接外部能力，subagents 负责分工，hooks 在指定时机触发处理。**

我平时更多使用 codex，所以这篇文章用 codex 写博客的过程，把这些概念串起来：

> 帮我写一篇介绍 redis 缓存的博客。参考已有文章的风格，用一个商品详情页的例子解释，保存到博客的文章目录。先给我看结果，得到授权后再推送。

本文依据截至 2026 年 10 月 6 日的官方文档整理。下面的目录和提示词是用法示例；是否能使用相应功能，还要看当前 codex 入口、版本和环境。

## 先把这些名词翻译成人话

可以把 codex 想成一位接到任务的编辑。他会查资料、动笔、检查，也可能请同事帮忙。

| 组件 | 白话理解 | 在写博客这件事里做什么 |
| --- | --- | --- |
| agent | 负责把事情做完的编辑 | 判断缺什么，安排下一步，检查结果 |
| `AGENTS.md` | 这个项目的注意事项 | 说明文章目录、文件名、标签和发布约定 |
| skills | 可反复使用的操作手册 | 规定怎样选例子、组织文章、核对事实 |
| tools | 编辑手里的工具 | 读取旧文章、查询资料、写文件、运行命令 |
| mcp | 外部能力的统一连接方式 | 接入文档服务或已有的仓库服务 |
| subagents | 分头工作的助手 | 一个核对资料，一个审查文章 |
| hooks | 到了指定时机触发的处理 | 在支持的工具事件后运行检查 |
| plugins | 打包好的扩展套件 | 一起安装技能和连接外部系统的能力 |

这些组件不要求全部出现。写一篇短文章，一个 agent 加上读取、编辑和检查工具，可能已经足够。

## agent：把需求推进成可交付的结果

大语言模型，也就是 llm，负责理解内容、生成文字和提出下一步操作。codex 这样的 agent 应用，还要执行工具、接收结果、管理上下文和控制流程。

例如，模型提出“读取三篇旧文章”，真正打开文件的是环境里的工具。工具返回文章后，模型才能判断我的博客通常怎样开头、举例和收尾。

这个工作循环可以简化为：

```text
理解任务和已有材料
      ↓
判断下一步需要做什么
      ↓
调用工具，查看结果
      ↓
检查是否达到目标
      ├─ 缺资料或发现错误 → 继续处理
      └─ 已达到目标 → 交付结果
```

在 redis 博客里，codex 写完后发现“缓存过期”和“内存淘汰”混在一起，就应该回到来源核对，再修正文中商品详情页的例子。

文件成功写入只是完成了一步。还需要确认内容正确、目录正确、检查通过，以及推送有没有得到授权。

## AGENTS.md：先告诉 codex 这个项目的规矩

我不想每次写博客，都重新解释一遍文章目录、标签规则和检查命令。这些长期约定适合写进仓库根目录的 `AGENTS.md`。

例如：

```markdown
# 博客约定

- 文章保存在 src/content/posts/。
- 文件名使用 YYYY-MM-DD-short-slug.md。
- 必须填写 title、description、pubDatetime、tags。
- 使用已有的相关标签，先解释用途，再展开术语。
- 保留已有修改，只处理当前文章。
- 按仓库现有命令检查；未经授权，不提交或推送。
```

文章开头这块标题、日期、标签等元信息，通常叫 frontmatter。

codex 会读取适用的项目说明。个人说明和项目说明可以叠加，目录越靠近当前工作目录的说明，越能补充更具体的约定。它不是无条件把仓库里所有同名文件都读进去。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

这时，三类信息的分工很清楚：

```text
AGENTS.md：这座博客的目录、格式和协作规则
写作 skill：把复杂概念讲清楚的方法
当前请求：这次写 redis 缓存，用商品详情页举例
```

说明文件给模型提供背景和要求。真正限制文件访问、网络和执行操作的，还包括运行环境的权限与审批机制。

## skills：把写博客的方法变成可复用手册

有了项目规范，codex 知道文章该放在哪里，但还需要知道怎样写得易懂。

这类反复使用的方法，可以整理成一个写作 skill。在本地 codex 项目中，一种官方支持的组织方式是：

```text
博客仓库/
├── AGENTS.md
├── .agents/
│   └── skills/
│       └── write-tech-blog/
│           ├── SKILL.md
│           ├── references/
│           │   └── writing-guide.md
│           ├── assets/
│           │   └── post-template.md
│           └── scripts/
│               └── check-frontmatter.py
└── src/
    └── content/
        └── posts/
```

`SKILL.md` 是核心，脚本、资料和模板都是可选的。下面是一个简化示例：

```markdown
---
name: write-tech-blog
description: 撰写面向初学者的中文技术博客，适用于需要例子、事实核对和文章格式检查的任务。
---

1. 读取适用的 AGENTS.md 和三篇相关旧文章。
2. 用一句话说明主题解决什么问题。
3. 选一个简单例子，贯穿主要概念。
4. 查官方资料，核对容易混淆的说法。
5. 按项目格式保存，仅运行与文章相关的检查。
6. 报告文件位置、修改内容和检查结果，遵守当前发布授权。
```

这个文件没有重新训练模型。它保存的是执行任务时可以参考的做事步骤。[官方 skills 文档](https://learn.chatgpt.com/docs/build-skills)。

在 codex cli 或 IDE 扩展中，可以通过 `/skills` 选择技能，或在提示词里用 `$` 指定已发现的技能。例如，在技能已经可用时输入：

```text
$write-tech-blog
写一篇 redis 缓存入门文章，用商品详情页贯穿全文。
先保存并检查，不提交或推送。
```

也可以只描述任务，让 codex 根据技能简介判断是否使用。技能不是放进文件夹后就保证生效：要确认它已被发现，适用范围也写得清楚。

### 为什么不把所有技能一次读进去

假设我还有分析日志、做表格、检查代码等几十种技能。写博客时把它们全部带上，会占用上下文，也容易混入无关要求。

上下文可以理解为模型这次处理任务时能够参考的材料。skills 采用按需展开的方式：

```text
先看技能名称和简介
      ↓
确认当前任务需要写博客
      ↓
读取写作技能的 SKILL.md
      ↓
需要模板或参考资料时，再读取对应文件
```

这像查一本手册：先看目录，再翻相关章节。用一个技能完成实际任务以后，还要回看结果，确认步骤有没有发挥作用。

## tools：让 codex 真正读文件、写文章和运行检查

tool 就是 agent 可以调用的操作能力。codex 能做哪些操作，取决于当前入口提供了什么工具，以及环境允许执行什么。

在博客任务里，操作可以很具体：

```text
读取文件：查看 AGENTS.md 和旧文章
查询资料：获取 redis 官方说明
编辑文件：保存新的 markdown 文章
运行命令：执行博客项目已有的检查
```

例如，在博客仓库里，codex 可以通过终端工具运行：

```bash
rg --files src/content/posts
git status --short
```

第一条列出可参考的文章，第二条了解当前工作区已有的修改。工具返回的是文件和状态，如何选文章、怎样避免覆盖别人的修改，还需要 agent 判断。

在有查询能力的环境里，可以查官方资料；没有网络或目标站点无法访问时，就应使用已经提供的材料，并说明哪些事实还没核实。

**skill 提供方法，tool 执行操作。** 把“核对官方资料”写进 skill，不会自动创造一个原本不存在的联网工具。

## mcp：把外部文档或服务接进来

mcp 是 model context protocol，也就是模型上下文协议。它让应用用统一的方式连接外部工具和上下文。

假设博客仓库已经在当前环境里，直接读文件或运行 git 就可以，不需要为了读一篇文章再搭一个 mcp server。

如果资料在外部系统，或者希望接入专门的文档查询服务，mcp 才可能派上用场：

```text
codex
  ↓
mcp client
  ↓
文档或仓库服务的 mcp server
  ↓
返回资料，或执行获准操作
```

mcp 规定怎样交流，tool 是接入后能够执行的具体操作。两者可以配合，但不是同一个东西。

在 codex cli 中，可以用下面的命令查看已经配置的服务：

```bash
codex mcp list
```

这是查看命令，不会替我安装服务或授予权限。本地 codex 支持通过配置连接本地进程或远端服务；云端能否使用同一服务，需要另外确认网络、连接和认证。[官方 mcp 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)。

例如，一个服务能读仓库文件，不代表它也能推送。mcp 把能力接进来，实际可做什么仍由服务和账号权限决定。

## subagents：把独立的核对工作交出去

当文章涉及很多概念时，可以明确要求 codex 使用子代理分工：

```text
请让两个子代理分别做以下工作：

1. 核对 redis 过期删除与内存淘汰的区别，
   返回触发条件、简单例子和官方来源。
2. 审查草稿中是否有术语没解释、例子前后矛盾的问题。

两个子代理都只返回意见，不修改文章。
等待结果后，由主代理整合并修订正文。
```

这段安排比“去研究一下 redis”更清楚。每个助手都有明确输入、边界和返回结果。

当前官方文档已经介绍 codex 的子代理工作流，可以直接请求分工，也可以由适用的项目或技能说明提出分工要求。子代理可以有自己的上下文和模型设置，不要求每个助手换一种模型。[官方 subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)。

它的好处是主对话不用塞满所有搜索记录。资料助手读很多材料，只返回相关事实和来源；主代理继续负责文章结构和最终结果。

不过，多代理会增加模型与工具的工作量。短文章通常不必分工，而且两个助手同时改同一段正文，反而容易冲突。比较稳妥的方式是让助手只读审稿，由主代理统一修改。

## hooks：把检查放到明确的触发时机

如果每次写完博客都要检查 frontmatter，仅靠一句“记得检查”，仍可能漏掉。

hook 的作用是：在支持的事件发生时，按配置运行处理。例如，当前 codex 官方文档列出的 `PostToolUse` 是工具执行后的事件，`Stop` 是当前回复结束时的事件。[官方 hooks 文档](https://learn.chatgpt.com/docs/hooks)。

在支持并已配置相应 hook 的 codex 运行环境里，可以设计这样的流程：

```text
codex 完成文章编辑
      ↓
匹配工具执行后的 hook
      ↓
运行文章检查脚本
      ↓
返回缺少 description 等问题
      ↓
codex 修正并重新检查
```

这只是流程示意。实际使用还要配置匹配范围、脚本和运行环境，确认编辑工具真的在覆盖范围内。hook 也不能检查工具尚未取得的资料是否真实。

对于写博客，我更容易先采用项目已有的检查命令。以这座博客为例：

```bash
pnpm build
pnpm check:content
```

前者检查并构建站点，后者检查构建出来的内容。它们是本博客的命令，其他项目应以自己的 `package.json` 为准。

还可以把检查放在 git hook 或 ci 中。这些是仓库或流水线的触发机制，和 codex 的生命周期 hook 要分清楚。尤其在云端任务里，先让 codex 主动运行检查、再让发布流水线检查，往往已经够用。

固定字段检查可以有明确规则；“文章是否易懂”仍需要审稿判断。自动触发不意味着所有判断都有唯一答案。

## plugins：需要反复安装时，再把配件打包

如果写作技能和一个资料服务经常一起使用，可以打包成 plugin，让其他人安装。

一个假想的博客插件可以包含：

```text
博客插件
├── 写作 skill
├── 文章模板与参考资料
└── 读取资料所需的 mcp 能力
```

plugin 主要解决分发和安装的问题。写一篇博客时，并不一定要先做插件；仓库里的一个写作 skill 就能保存方法。

当前官方文档区分了各入口：codex cli 和桌面端有插件入口，IDE 扩展不支持插件。插件可以包含 skills、mcp 能力和 hooks，但云端编排的 chatgpt work 不支持插件 hooks，安装插件也不会自动把脚本部署到执行环境。[官方 plugins 文档](https://learn.chatgpt.com/docs/plugins)。

因此，安装前要看自己实际用的入口和插件需要的权限。不要把“插件已安装”“外部账号已连接”“脚本可以运行”当成同一个状态。

## 本地和云端：方法可以相似，环境需要分别确认

codex 的名字相同，工作的位置和可用能力却不一定相同。

| 入口 | 写博客时需要确认什么 |
| --- | --- |
| codex cli | 当前终端所在的仓库、文件权限、已有命令和配置 |
| IDE 扩展 | 当前编辑器工作区、技能和 mcp 是否可用；不套用插件安装流程 |
| codex cloud | 云端准备好的仓库和依赖、网络范围、认证与任务保存位置 |
| chatgpt work 中的云端执行 | 当前提供的技能与连接工具；不默认继承本地 codex 的配置或插件 hooks |

本地项目的 `.agents/skills/` 目录适合保存项目技能。把相关文件放进仓库，便于一起管理，但云端任务是否发现并加载了它，仍要看该入口的技能机制。

官方云端环境说明也强调，任务使用自己的准备环境和文件状态，网络访问有独立设置。[官方云端环境说明](https://learn.chatgpt.com/docs/environments/cloud-environments)。

例如，我在本机配好了一个文档 mcp 服务，并不能据此断定云端也能连接。正确的做法是让目标环境实际读取文件、查询来源或运行命令，再根据结果继续。

## 把写博客的全过程走一遍

现在回到开头的请求。一种合理的 codex 工作流程是：

1. **确认环境和已有修改**：找到博客仓库，查看当前分支和工作区状态。
2. **读取项目规范**：从适用的 `AGENTS.md` 确认目录、元数据、文风和检查要求。
3. **使用写作 skill**：按技能选择例子、安排结构、核对容易混淆的概念。
4. **用工具读取来源**：读旧文章和官方资料，需要外部能力时使用已接入的 mcp。
5. **按需要请求子代理审稿**：让助手返回事实核对和审稿意见，主代理整合。
6. **保存并检查文章**：检查元数据、链接、代码围栏和生成页面，修正发现的问题。
7. **交付结果并按授权推送**：说明实际文件、差异和检查结果；获得发布授权后，仅提交这篇文章。
8. **确认远端与部署**：核对推送后的提交，再确认自动发布是否成功。

其中，第 4 步可能反复发生，第 5 步可以省略，第 6 步也不要求一定使用 hook。

如果没有推送授权，工作可以停在保存和交付；如果已经明确授权，就按约定继续。技能里的步骤应服务于当前任务，而不是反复要求用户确认已经说清楚的事情。

## 什么时候该用哪一个

遇到问题时，可以先判断缺的是哪一部分：

| 遇到的问题 | 优先考虑 |
| --- | --- |
| 不知道当前项目的目录、格式和协作约定 | 补充 `AGENTS.md` |
| 每次都要重复交代同一套写作方法 | 整理成 skill |
| 没有读文件、查询资料或运行命令的能力 | 确认可用 tool 和环境 |
| 需要接入外部系统 | 看是否有合适的 mcp 或连接工具 |
| 独立核对任务很多，主对话材料太杂 | 明确请求 subagent 分工 |
| 某个检查要在特定事件发生时执行 | 使用已验证的 hook，或仓库自己的触发机制 |
| 希望把技能和连接能力反复安装、分享 | 打包成 plugin |

刚开始，可以先把“读规范 → 找资料 → 写文章 → 做检查”这条流程跑通。

理解这些组件，关键是看清它们分别补上哪一部分能力。对我这样的博客写作场景，`AGENTS.md` 保存项目约定，skill 保存方法，工具完成操作，再按需要增加连接、分工和自动检查，就已经能把一句需求变成可核对的结果。

学习 slurm 时，最容易混淆的往往不是命令拼写，而是几层关系：提交作业是不是已经运行，申请四个 cpu 是不是会启动四份程序，拿到两台机器是不是程序就能自动并行。

本文用一个 python 日志统计任务贯穿讲解。先认识节点、作业、分区和核心组件，再逐步看查询、提交、资源参数、数组、依赖和多节点；最后把单节点、多节点安装结构和完整作业流程串起来。

重点是理解 slurm 自身。命令和配置用来说明“是什么、什么时候用、输出怎样读”，不把环境搭建当作学习门槛，也不扩展为通用 python 环境管理教程。

文中的主机名、作业号和输出都是教学示例，没有在真实集群执行。普通用户命令以已配置好的登录节点为前提；安装和服务设置属于管理员工作。具体选项以所用版本与集群规则为准。

## 1. slurm 解决什么问题

### 从一个需要计算的任务说起

假设有一个 python 程序，要统计一批日志的总行数。只有自己使用一台电脑时，直接运行它通常就够了。问题出现在多人共用若干台计算服务器时：谁先运行？每个人可以使用多少 cpu 和内存？一台机器已经忙了，任务应该去哪里？任务运行几个小时后，怎样知道是否结束？

如果每个人都自己找机器、直接启动程序，很容易发生两种情况：有些机器被同时启动的程序挤满，另一些机器却没有被有效使用；也很难按统一规则决定谁可以用哪些资源。

**slurm 是一套管理计算资源、安排作业运行的软件。** 用户向它描述需要什么资源、运行什么程序；它根据可用资源与集群规则安排执行，并提供观察与管理过程的方式。

这里先解释两个词。**资源**是程序需要使用的计算条件，例如 cpu、内存和 gpu。**提交**是把运行请求交给 slurm，不等于程序已经开始执行。

### 一份任务怎样走完一生

沿用“统计日志行数”的例子，暂时只考虑一个程序在一台机器上运行。

1. **描述任务。** 用户说明要运行日志统计程序，并给出资源要求，例如一份 cpu 计算能力、足够的内存和最长运行时间。
2. **提交请求。** slurm 接收请求，分配一个作业号。作业号就像这次运行的查询编号；以后可以用它了解运行情况。
3. **等待安排。** 如果资源正被其他作业占用，或者当前规则还不允许启动，这次请求会等待。
4. **分配资源。** 条件满足后，slurm 把某台计算机器上的一部分资源交给该作业使用。
5. **启动并运行程序。** 程序开始读取日志、统计行数；slurm 负责相应的启动和过程管理。
6. **结束并释放资源。** 程序完成或被终止后，资源可以再分给别的作业。输出、退出状态和历史记录是判断结果的重要线索。

例如，这次运行被分配了作业号5203，最终安排在名叫`node02`的机器上。5203代表这次作业，`node02`代表执行它的机器；这两个名字对应不同对象。

### “安排运行”与“程序计算”分别是谁做

slurm 可以决定日志统计程序何时运行、用哪台机器、获得哪些资源。但读取日志、计算行数以及输出统计结果，仍是 python 程序自己的逻辑。

可以类比为共享会议室：预约系统决定什么时候、谁能使用哪个房间；会议里讨论什么，不由预约系统决定。slurm 比预约系统承担更多启动和管理职责，但这个类比有助于分清“管理资源”与“执行业务逻辑”。

因此，申请更多资源不保证普通程序自动变快。一个只按顺序读取文件的程序，不会因为获得两台机器，就自动把文件拆成两半处理。

### 它适合哪些场景

常见场景包括大量相互独立的数据处理、科学计算、长时间批处理、模型训练和需要多台机器协作的程序。它们的共同点是：运行有明确的资源需求，常常需要排队，并且希望按统一规则管理。

slurm 也可以支持用户实时发起任务，但“实时发起”不意味着立即获得资源。它首先仍是一个共享计算资源管理系统。

这一节先建立主线：**提出资源与程序需求，等待调度，获得资源，运行，结束。** 下一节给这些对象正式命名，分清节点、作业、分区与队列。

参考：[官方概览](https://slurm.schedmd.com/overview.html)、[用户入门](https://slurm.schedmd.com/quickstart.html)。

## 2. 节点、作业、分区与队列

### 四个对象，各自回答什么问题

\*\*节点（node）\*\*是 slurm 管理的一台计算机器。\*\*作业（job）\*\*是一次受 slurm 管理的运行请求及其生命周期。\*\*分区（partition）\*\*把一组节点组织成可供作业选择的逻辑资源范围，并附带使用规则。\*\*队列（queue）\*\*描述等待或运行中的作业集合，不是一台额外的服务器。

| 对象 | 关注的问题 |
| --- | --- |
| 节点 | 在哪台机器上执行 |
| 作业 | 哪一次运行 |
| 分区 | 从哪组资源中选择，遵守什么规则 |
| 队列 | 哪些作业正在等待或运行 |

### 用三台机器说明

假设集群有三台计算节点：`node01`、`node02`和`node03`。管理员把前两台放进`cpu`分区，第三台放进`gpu`分区。这里的`cpu`与`gpu`只是管理员起的分区名，不是 slurm 强制规定的名字。

alice 提交日志统计作业5203，选择`cpu`分区。含义是：请在这个分区允许的节点范围中，寻找符合要求的资源。通常不是用户已经指定了其中某台机器。

如果`node01`忙，`node02`有合适资源，slurm 可能安排作业到`node02`；如果两台都暂时不满足要求，作业就等待。此时作业已经存在，但还没有在计算节点上开始运行。

### 分区不等于把物理机器切开

“分区”这个中文容易让人联想到磁盘分区。slurm 的分区首先是一种逻辑组织方式：可以规定最长运行时限、允许的用户或用户组、节点范围等。

同一个节点也可能同时出现在两个分区。例如：

| 分区名 | 包含节点 |
| --- | --- |
| `cpu` | `node01`、`node02` |
| `short` | `node01` |

这不代表有三台机器。`short`可能只是向同一台`node01`提供另一套较短时限规则。两个分区指向的物理资源仍需要统一管理，不能把它们重复当成独立机器计数。

### 作业也不等于一个文件

同一份脚本可以提交多次，每次得到不同作业号。这些是不同作业，可能在不同时间或节点运行。反过来，一次作业也可以管理多个程序进程；这里的“进程”就是正在运行的一份程序实例。

现在不必引入复杂的并行参数。只要记住：脚本是运行说明文件，作业是一次受管理的运行，节点是机器。

### 登录节点又是什么

登录节点是用户连接集群后使用命令、准备提交材料的入口。计算节点主要承担实际计算。它们是角色，可以部署在不同机器上，小型系统也可以在一台机器中合并。

“在登录节点提交作业”并不表示作业就在登录节点计算。提交入口和执行位置是两回事。安装角色由管理员安排，普通用户通常使用已经配置好的入口即可。

### 为什么空闲不等于马上能运行

某节点有空闲 cpu，仍可能不符合这个作业的其他要求，例如内存不足、用户没有该分区权限、申请时间超过规则、当前有其他应优先安排的作业。cpu 空闲只是条件之一。

可以把队列理解为“等待安排的运行清单”，但不要把它想成绝对按到达先后移动的单列队伍。slurm 还需要结合资源是否匹配和站点规则判断。

这一节要记住：**节点是机器，作业是一次运行，分区限定可选资源和规则，队列体现作业等待与运行情况。** 下一节看负责管理这些对象的服务。

参考：[用户入门中的架构与实体](https://slurm.schedmd.com/quickstart.html)。

## 3. 三个核心组件怎样协作

### 先给服务一个直白定义

**后台服务**是长期运行、等待处理请求的程序。用户不需要每次提交作业都手动启动它。slurm 把“全局安排”和“机器上的执行管理”分给不同组件。

| 组件 | 主要职责 |
| --- | --- |
| `slurmctld` | 控制服务，维护全局作业与资源状态，作出分配决策 |
| `slurmd` | 计算节点服务，接收执行请求，管理这一节点的启动工作 |
| `slurmstepd` | 具体执行步骤的管理进程，负责该步骤的程序启动、输入输出和结束处理等 |

组件名中的`d`常表示长期后台服务。不过`slurmstepd`与前两者的生命周期不同：它通常按执行步骤需要由 slurm 创建，步骤结束后退出，不是管理员在每台机器上另行长期启动一份就够了。

### 先只跟踪一台机器上的一个程序

假设日志统计作业5203最终在`node02`执行，程序仍只是普通 python 程序。为了避免用未解释的命令来解释组件，这一节只讲事情如何流转。

1. 用户从提交入口发送运行请求。
2. `slurmctld`检查请求，维护作业记录，判断什么时候能分配资源。
3. 可以运行时，控制服务确定使用`node02`上的哪些资源，并推动启动流程。
4. `node02`上长期运行的`slurmd`参与接收与落实启动请求。
5. 对应的`slurmstepd`负责这次具体执行步骤，启动程序、处理输出并等待其退出。
6. 结束信息被汇总回 slurm，资源随后释放。

这是职责层面的简化，不表示真实通信只有一条固定的“控制服务逐条转发所有内容”的链。用户命令、控制服务和节点服务会按不同阶段协作；这里先把职责分清。

### 为什么还需要 slurmstepd

如果把`slurmd`看作“这个计算节点的常驻接待与执行管理入口”，`slurmstepd`就负责某一场具体工作的现场管理。节点可以先后或同时承载多个作业，不适合把每个程序的全部生命周期都混在一个无法区分的执行现场中。

它会参与启动进程、连接程序的输入与输出、等待退出以及与资源使用相关的管理。业务计算仍由 python 程序完成。`slurmstepd`不会理解日志内容，也不会替 python 决定怎样统计行数。

### 作业步骤是什么

\*\*作业步骤（job step）\*\*是一个作业内部的一次受 slurm 管理的执行单元。先有“这个作业获准使用哪些资源”，再有“在这些资源里启动哪一组程序”。后者可以作为步骤被管理。

批处理作业会先运行一份脚本。slurm 把管理这份脚本的特殊步骤称为**batch 步骤**；`batch`在这里就是“批处理脚本”的意思。即使脚本内部只直接启动一个 python 程序，也已经有管理脚本执行的 batch 步骤。

因此，**没有在脚本里显式写某个启动命令，也不等于没有 slurmstepd。** 如果只把它与某个启动命令绑定，就容易忽略批处理脚本本身也需要执行管理。

后续第7节会在解释命令之后，说明怎样在已有作业中另外创建普通步骤。这里不提前塞入命令参数、多节点和任务数量。

### 三个角色也不必是三台机器

控制角色运行`slurmctld`，计算角色运行`slurmd`，提交角色提供用户命令。它们可以在三类机器上分开，也可以在单节点环境中合并。`slurmstepd`跟随具体执行出现在相应计算节点上。

不要根据组件名的数量推算需要几台服务器。部署角色与执行进程的数量是两个层次。

这一节的核心是：**slurmctld 负责全局安排，slurmd 负责节点侧接收与启动管理，slurmstepd 负责具体步骤的生命周期。** 下一节先学习观察集群的命令，不要求搭建任何服务。

参考：[slurmctld](https://slurm.schedmd.com/slurmctld.html)、[slurmd](https://slurm.schedmd.com/slurmd.html)、[slurmstepd](https://slurm.schedmd.com/slurmstepd.html)、[作业启动设计](https://slurm.schedmd.com/job_launch.html)。

## 4. 用 sinfo 查看分区和节点

### sinfo 回答的是资源概况

`sinfo`用于查询 slurm 中的分区与节点信息。它是查询命令，不会申请计算资源，也不会启动日志统计程序。

普通用户通常在配置好的登录节点输入它。前提是命令已安装，能找到集群配置并访问相关服务。能看到哪些分区，还受站点的隐藏与访问策略影响。

先看一份为手机阅读拆开的示例。真实默认输出通常是一张宽表，这里把字段分成两部分；两部分描述同一个时刻。

```text
PARTITION AVAIL TIMELIMIT
cpu*      up    1:00:00
cpu*      up    1:00:00
gpu       up    2:00:00
```

```text
NODES STATE NODELIST
1     idle  node01
1     mix   node02
1     idle  node03
```

### 逐项读懂

`PARTITION`是分区名。`cpu*`中的星号表示默认分区：提交时没有另选分区，通常会使用默认值，仍需满足集群规则。星号不是分区名字本身的一部分。

`AVAIL`表示分区的可用状态。示例`up`可理解为该分区当前开放相应调度使用；它不证明这个用户的某个作业一定马上获批。

`TIMELIMIT`表示分区允许的最大作业运行时限。`1:00:00`是一小时，不是“还要排队一小时”，也不是节点已运行了一小时。

`NODES`表示**这一行汇总的节点数量**。这里每行都是1个节点。

`STATE`是节点状态。`idle`表示节点当前处于空闲状态；`mix`表示 cpu 资源有一部分分配给作业、另一部分未分配。节点还有内存等其他资源，不能仅从`mix`算出某个作业还可申请多少。

`NODELIST`列出对应节点。若显示`node[01-03]`，就是`node01`、`node02`、`node03`的缩写。中括号中的范围不是新机器名，而是紧凑的名称表达方式。

### 为什么同一个分区出现多行

示例中的`cpu`包含两个节点，但两个节点状态不同。`sinfo`把同一分区中状态相同、可以归并的信息显示在一行，因此分成了`idle`和`mix`两行。

这不是两个不同的`cpu`分区，也不是作业排队次数。读这一类输出时，应把分区名、状态和本行节点数连起来看。

再结合上一章的重叠分区：如果`node01`同时属于`cpu`和`short`，它可能在两个分区的输出中出现。把所有行的`NODES`直接相加，会把同一台机器重复计算。

### 只看一部分信息

```text
sinfo --partition=cpu
```

`--partition=cpu`表示只查询名为`cpu`的分区。它是筛选查询结果，不是替自己预留这个分区。

```text
sinfo --nodes=node01
```

`--nodes=node01`表示只查看涉及该节点的信息。这里参数名称与以后资源申请中出现的“节点”有关，但在`sinfo`中，它只影响查询范围。

### 观察结果怎样帮助理解下一步

假设`cpu`开放，`node01`空闲。这能告诉我们集群中存在一台当前空闲的候选机器。但作业还可能要求更大的内存、其他硬件或不同权限；也可能受优先级和限额影响。

所以`sinfo`适合回答“资源大致是什么样”，不能独自回答“我的作业为什么等待”。下一节的`squeue`会把观察对象转向具体作业。

这一节要记住：**先看分区，再看每行节点数量、状态和名称；空闲与开放都是资源信息，不是立即运行承诺。**

参考：[sinfo 官方手册](https://slurm.schedmd.com/sinfo.html)。

## 5. 用 squeue 查看作业与排队

### 从资源切换到一次具体运行

`squeue`显示 slurm 当前管理的队列信息，主要用来观察等待或运行中的作业。它不会提交程序，也不会取消作业。

普通用户在登录节点可以看到权限允许的作业列表：

```text
squeue
squeue --me
squeue --jobs=5203
```

第一条查询默认范围；`--me`只筛选当前用户自己的作业；`--jobs=5203`只筛选这个作业号。三条是不同查询示例，不是必须依次执行的一组操作。

假设用户名为`alice`，日志统计作业名称简写为`count`，作业号是5203。

### 等待时的输出

默认表包含很多列，这里拆成两段，表示同一行：

```text
JOBID PARTITION NAME  USER
5203  cpu       count alice
```

```text
ST TIME NODES NODELIST(REASON)
PD 0:00 1     (Resources)
```

`JOBID`是作业号。`PARTITION`是选择的分区。`NAME`是便于识别的作业名，名字可以重复，不能替代作业号。`USER`是作业所有者。

`ST`是简写状态。`PD`来自`PENDING`，表示等待开始。`TIME`是**已经运行的时长**；这个作业尚未开始，所以是`0:00`。它不是排队等待时间，不能据此判断刚提交还是已经等了两小时。

等待时，`NODES`通常表示作业要求的最少节点数。示例中的1不表示已经拿到一台机器。

最后一列的标题是`NODELIST(REASON)`：运行时常显示节点；等待时常用括号显示原因。`(Resources)`表示此次调度观察中，所需资源还不能提供。

### 运行时，同一个作业怎样变化

过一段时间，作业可能显示为：

```text
JOBID PARTITION NAME  USER
5203  cpu       count alice
```

```text
ST TIME NODES NODELIST(REASON)
R  2:15 1     node02
```

`R`来自`RUNNING`，表示已获得资源并处于运行阶段。`2:15`表示已经运行2分15秒。此时`NODES=1`是已分配的节点数量，`node02`是具体节点。

现在把两种情况对比，就能看清默认输出的双重含义：

| 列 | 等待与运行时的区别 |
| --- | --- |
| `NODES` | 等待看申请，运行看已分配 |
| 最后一列 | 等待常看原因，运行常看节点 |

### resources 与 priority 分别是什么意思

`Resources`关注资源不能满足当前需求。例如，需要一台内存足够的节点，但合适节点正被占用。

`Priority`关注安排先后：相关范围内存在应更早被考虑的作业。**优先级**在这里先理解为决定“谁先被安排”的规则；它不一定只按提交时间排序。

一份作业可能同时存在多个阻碍，界面不一定一次列出全部原因。随着调度过程变化，显示的原因也可能改变。某一时刻看到`Resources`，不能断言权限、限额和其他条件都已永久排除。

### 列表里消失，代表成功了吗

不能。`squeue`主要观察当前队列，不是长期历史档案。作业完成、失败、取消或超时后，都可能不再出现在默认列表中。

只剩表头也只说明本次筛选没有匹配的可见记录。后续要结合历史记录和输出理解结果，而不是把“查不到”当作“已经成功”。

这一节要记住：**先用作业号锁定对象，区分等待与运行，time 看已运行时长，消失不等于成功。** 下一节再介绍怎样提交脚本。

参考：[squeue](https://slurm.schedmd.com/squeue.html)、[排队原因](https://slurm.schedmd.com/job_reason_codes.html)。

## 6. 用 sbatch 提交脚本

### 为什么要把运行说明写成脚本

**批处理**就是把要执行的命令预先写好，交给系统在合适时机运行。用户不需要一直守着终端，等待资源空出来再手动启动。

`sbatch`负责提交批处理脚本。脚本包含两类内容：一类告诉 slurm 这次运行的名称、分区和时限；另一类是获得资源后真正执行的普通命令。

先采用最简单的情况：只需要一个程序在一台计算节点上运行，python 已经安装，程序和输入文件在计算节点可访问的位置。示例目录称为`/shared/count`，名字中的`shared`只表达示例前提，不会自动让目录共享。

### 一份最小但说得清的脚本

文件`count.sbatch`：

```text
#!/bin/bash
#SBATCH --job-name=count
#SBATCH --partition=cpu
#SBATCH --time=00:10:00
#SBATCH --output=count-%j.out

python count.py
```

`#!/bin/bash`说明脚本由 bash 解释执行。bash 就是读取并依次执行这些 shell 命令的程序。

以`#SBATCH`开头的行由 slurm 读取，是**作业指令**。对 bash 来说它们像注释，但 slurm 会在脚本运行前把这些选项解释为提交要求：

| 指令 | 意思 |
| --- | --- |
| `--job-name=count` | 这次作业显示为 count |
| `--partition=cpu` | 在 cpu 分区的规则下申请资源 |
| `--time=00:10:00` | 最长运行10分钟，不含排队时间 |
| `--output=count-%j.out` | 把标准输出保存到含作业号的文件 |

这里的标准输出，就是程序输出普通文本的通道，例如 python 的`print`打印的内容。`%j`是 slurm 替换的作业号占位符。若作业号是5203，输出文件名就是`count-5203.out`。它不是 shell 变量，也不是取模运算。

最后一行`python count.py`才是真正执行的程序命令。本例没有显式 cpu、节点数量参数，依赖集群默认值；后续学习数量语义之后，再写完整的资源申请，避免先摆模板、后补含义。

### python 例子做了什么

`count.py`：

```text
with open("input.log", encoding="utf-8") as f:
    lines = sum(1 for _ in f)

print(f"lines={lines}")
```

程序逐行读取`input.log`，每读一行累计1，最后打印总行数。`with`确保文件读取结束后被关闭；`encoding`指定按 utf-8解释文本。本例假定日志就是这种编码。

假如示例文件有12000行，程序输出就是：

```text
lines=12000
```

这行文本来自 python，不是 slurm 自己计算的结果。slurm 只是按输出配置保存它。

### 提交成功到底确认了什么

普通用户从示例工作目录提交：

```text
sbatch count.sbatch
```

示例回应：

```text
Submitted batch job 5203
```

它确认脚本已被接收并获得作业号，不确认资源已经分配，更不确认程序成功。接下来用上一节的`squeue --jobs=5203`观察等待或运行即可理解状态。

slurm 会传送批处理脚本本身，但不会因此自动搬运`count.py`和`input.log`。本例两者都必须在执行节点可访问的位置。默认工作目录通常沿用提交目录，因此这里明确假设在`/shared/count`提交，避免把程序路径问题混进资源调度。

### 两个常见误会

第一，批处理脚本只会在分配节点中的一个节点上启动一份，不会因为以后申请多个节点，就自动在每台机器各运行一份完整脚本。

第二，`#SBATCH`指令应放在真正执行的命令之前。slurm 遇到首个不是注释、也不是空白的命令行后，不再继续处理后面的这些指令；指令中的 shell 变量也不会像普通命令那样展开。

这一节要记住：**sbatch 提交运行说明，sbatch 行描述作业，脚本命令负责计算；拿到作业号只说明已接收。** 下一节把申请资源和启动程序进一步拆开。

参考：[sbatch 官方手册](https://slurm.schedmd.com/sbatch.html)。

## 7. srun 与 salloc——申请资源和启动程序

### 先分清三件事

**申请资源**：告诉 slurm 希望使用什么，例如一台节点上的一份运行资源。**资源分配**：slurm 批准后，确定在一段时间内哪些资源属于这次作业。**启动程序**：在这些已获准的资源上真正创建程序进程。

申请不等于获批，获批也不等于某个业务程序已经启动。这个区别是理解这一节所有命令的前提。

**salloc**主要用于取得一份资源分配，再在该分配存续期间组织执行。**srun**用于在 slurm 管理下启动程序；如果当前还没有适用的资源分配，它也可以先发起申请。

### 先用一个最简单的程序观察执行位置

`hostname`是普通 linux 命令，用来输出当前执行这条命令的机器名称。它不属于 slurm，但这里用它能直接看出 slurm 把程序放到了哪里。

普通用户从登录节点发起：

```text
srun --nodes=1 --ntasks=1 --time=00:10:00 hostname
```

先解释这三个参数：`--nodes=1`请求一台节点；`--ntasks=1`启动一个任务，这里可理解为一份`hostname`程序进程；`--time`给这次资源分配设置最长时限。`hostname`是获准后要执行的程序。

没有现成分配时，`srun`可以申请、等待，获准后启动程序。假想最终输出：

```text
node02
```

这表明示例命令在`node02`执行。终端等到了这个输出，不代表所有同类请求都无需排队。

### salloc 得到资源以后，shell 在哪里

现在换一种组织方式：

```text
salloc --nodes=1 --ntasks=1 --time=00:10:00
```

示例回应：

```text
salloc: Granted job allocation 5204
```

`allocation`就是这份已批准的资源分配。未显式给程序时，`salloc`会启动用户默认 shell，shell 结束时释放分配。

在没有启用特殊交互入口配置的常见方式下，这个 shell 仍在发起命令的登录节点，并没有因为获准使用`node02`而自动“搬家”。例如，普通`hostname`可能仍输出`login01`；在这个 shell 中通过 slurm 启动：

```text
srun --ntasks=1 hostname
```

才会得到示例结果`node02`。有些集群配置会把交互 shell 放到计算节点，所以“永远留在登录节点”也不准确；本例先明确采用普通的本地 shell 模式。

同一份分配内可以先后运行多个`srun`。这适合需要连续发起几段程序、希望保持同一资源分配的情况。示例中退出由`salloc`启动的 shell：

```text
exit
```

会结束会话并释放资源。`exit`是 shell 退出命令，不是另一个资源申请命令。

### sbatch 脚本中为什么有时也写 srun

第6节的脚本直接写：

```text
python count.py
```

在单节点简单情况下，python 作为批处理脚本的子进程在脚本所在节点运行。这不表示“绕过 slurm”：外层批处理作业已经由 slurm 安排，并有 batch 步骤管理。

也可以写：

```text
srun --ntasks=1 python count.py
```

此时`srun`在已有资源分配中创建一个普通作业步骤，并启动一份 python 进程。**步骤**是作业内的一次受管理执行；外层作业决定资源范围，步骤组织这次程序启动。

如果作业号是5204，历史里可能出现`5204.batch`与`5204.0`：前者是批处理脚本步骤，后者是第一个普通步骤。它们属于同一个作业，不是重新提交的两个独立作业。

### 什么时候确实需要它

当需要在分配的多个节点上启动任务，或者希望程序作为独立步骤被 slurm 启动、记录、控制时，`srun`的意义更加明显。它提供的是启动和管理机制，不会自动给 python 增加并行算法。

| 命令 | 这一节常见使用方式 |
| --- | --- |
| `sbatch` | 提交预写脚本，稍后批量执行 |
| `salloc` | 先获得分配，再组织多次执行 |
| `srun` | 启动任务，无现成分配时也可先申请 |

这一节要记住：**salloc 取得分配，srun 启动受管理的程序，sbatch 提交批处理脚本。** 这解释了资源申请、程序启动和作业步骤的关系；下一节学习取消和查询详情。

参考：[srun](https://slurm.schedmd.com/srun.html)、[salloc](https://slurm.schedmd.com/salloc.html)、[作业启动流程](https://slurm.schedmd.com/job_launch.html)。

## 8. 取消作业与查看详情

### 查询与改变状态要分开

`squeue`让人看到当前作业列表；如果需要更多细节，可以使用`scontrol show job`。`scontrol`既有查询能力，也有修改能力，这一节只使用只读的`show job`。

`scancel`用于取消作业。取消是改变状态的操作：等待的作业不再按原请求继续运行，正在运行的作业则进入终止与清理过程。它不等于暂停，也不自动保存程序处理到一半的业务状态。

以下都假设是普通用户在登录节点管理自己的作业5203。查看范围和管理权限受集群策略限制，管理员通常具有更大权限。

### 看一份作业详情

```text
scontrol show job 5203
```

其中`show`表示显示，`job`表示对象类型，5203指定对象。示例摘取必要字段，并分行展示：

```text
JobId=5203
JobName=count
UserId=alice(1001)
Partition=cpu
JobState=PENDING
Reason=Resources
NumNodes=1
NodeList=(null)
```

`JobId`与`JobName`分别是作业号和名称。`UserId`显示用户名及数字用户编号；linux 在内部用数字编号识别用户。

`JobState=PENDING`表示等待，`Reason=Resources`解释当前原因。`NumNodes=1`在这一等待场景中描述节点请求；`NodeList=(null)`表示还没有分配节点列表，不能把它理解成节点名就叫 null。

作业运行后，示例可能变为：

```text
JobState=RUNNING
Reason=None
NodeList=node02
NumNodes=1
RunTime=00:02:15
TimeLimit=00:10:00
```

`Reason=None`表示此处没有等待原因。`RunTime`是已运行时长；`TimeLimit`是运行时限。二者一个描述已经发生的时长，一个描述允许的上限，不能互换。

不同版本与状态可能出现不同字段或格式，示例只用于理解含义，不是要求每个集群逐字一致。

### 取消等待中的作业

```text
scancel 5203
```

这表示请求取消这个作业。若它还在等待，就不再按这份请求继续启动。以后重新提交同一脚本，是另一个作业，不是把原作业自动接上。

命令没有输出，通常不表示程序已成功运行，也不是业务结果。它只是可能没有额外消息；实际状态仍应结合查询和后续历史记录判断。

### 取消运行中的作业

命令形式相同，但后果不同：slurm 会按自身机制向执行侧传达终止，处理进程并清理资源。清理可能需要时间，因此不必期待请求返回的瞬间，所有节点信息就全部消失。

日志文件可能已经写入一部分，程序输出可能不完整。某个结果文件存在，并不能证明这个被取消的作业完成了全部计算。

这一节只展示单个明确作业号，避免把按用户名或宽泛条件批量取消混进初学示例。权限不足时，slurm 会拒绝操作，而不是因为用户知道作业号就允许取消别人的作业。

### 作业结束以后还能一直 show 吗

控制服务为了管理当前运行，不会保证永久保存每个作业的全部详情。结束一段时间后，`scontrol show job`可能找不到它。这时需要历史记账信息；下一章介绍的`sacct`正是为此服务。

这一节要记住：**show job 是看当前详情，scancel 是取消；取消不是暂停，输出文件存在也不等于成功。**

参考：[scontrol](https://slurm.schedmd.com/scontrol.html)、[scancel](https://slurm.schedmd.com/scancel.html)。

## 9. 历史记录、标准输出、错误输出与退出码

### 作业消失后，分别到哪里看

`sacct`查询 slurm 的作业记账记录。**记账**不只指费用，而是记录作业什么时候运行、使用了什么资源、怎样结束等信息。

前提是管理员配置了可用的记账存储和相关采集。常见部署使用`slurmdbd`把记录保存到数据库，后面会解释这个组件；这一节先知道：不是安装了`sacct`命令，就自动拥有完整历史。可见范围、数据保留时间和可用字段也由站点配置决定。

普通用户在登录节点查询自己的作业，例如：

```text
sacct --jobs=5203 --format=JobID,State,ExitCode
```

`--jobs`指定作业；`--format`选择要显示的列，逗号连接字段名。这里不引入大量资源统计，只看作业号、状态和退出码。

简化示例：

```text
JobID      State      ExitCode
5203       COMPLETED  0:0
5203.batch COMPLETED  0:0
5203.0     COMPLETED  0:0
```

第一行是整个作业；`.batch`是脚本步骤；`.0`是脚本通过`srun`启动的普通步骤。其他配置下可能还出现别的特殊步骤；没有显式`srun`的简单脚本也不一定有`.0`这一行。

### 什么是标准输出与错误输出

程序通常有两个文本输出通道。\*\*标准输出（stdout）\*\*常用于普通结果，例如`lines=12000`；\*\*标准错误（stderr）\*\*常用于诊断信息，例如 python 异常。

这是一种通道区分，不是“输出文件一定正确、错误文件一定表示失败”的绝对规则。程序也可能把进度写入 stderr，或者把错误说明打印到 stdout。

`sbatch`默认把两类输出送到`slurm-%j.out`，其中`%j`替换作业号。也可以明确分开：

```text
#SBATCH --output=count-%j.out
#SBATCH --error=count-%j.err
```

假设5203在提交目录运行，文件就是`count-5203.out`和`count-5203.err`。相对文件名按照作业工作目录解释；绝对路径则指定固定位置。父目录必须在打开输出时可用，slurm 不会自动创建任意一层目录。

这些文件保存的是程序输出，不是`sacct`数据库记录。`sacct`通常不会直接显示整份 python 日志，也不会自动保存程序写出的所有结果文件。

### 退出码后面为什么有冒号

程序结束时会向系统返回一个数字，叫**退出码**。通常0表示程序报告成功，非0表示它报告失败；具体非0值的含义要看程序。

slurm 常把`ExitCode`显示为“退出码:信号编号”。**信号**是操作系统通知进程发生某种事件的机制，其中一些会终止进程。

| 示例 | 解释 |
| --- | --- |
| `0:0` | 返回0，未记录导致终止的信号 |
| `1:0` | 返回1，表示失败，未记录终止信号 |
| `0:9` | 示例记录中因9号终止信号结束，不能当作成功 |

冒号两边不是“成功步骤数:失败步骤数”，也不是比例。观察时必须结合`State`和日志。

### 为什么0:0仍不等于业务正确

对`sbatch`作业，slurm 捕获的是批处理脚本的退出码。脚本若没有适当处理失败，可能出现：前面程序报错，后面一条普通命令成功，最后脚本整体返回0。

例如下面只用来解释风险：

```text
python count.py
echo "script ended"
```

`echo`只是输出一行文本。即使 python 失败，脚本也可能继续执行它，最终以最后一个命令的成功状态结束。因此看到`COMPLETED`、`0:0`，仍需要检查程序输出和必要的步骤记录。结果是否符合业务预期，更不是 slurm 能够独自判断的。

这一节要记住：**sacct 看记录，输出文件看程序说了什么，退出码看程序怎样报告结束；三者互相补充。** 下一节再把资源数量讲清楚。

参考：[sacct](https://slurm.schedmd.com/sacct.html)、[退出码说明](https://slurm.schedmd.com/job_exit_code.html)、[记账体系](https://slurm.schedmd.com/accounting.html)。

## 10. 节点数、任务数与每任务 cpu 数

### 三个参数分别数什么

第7节用过一个节点、一个任务。现在进一步区分：节点是机器；任务通常对应 slurm 启动的一份程序进程；每任务 cpu 数是为每个任务预留多少 cpu 资源。

| 参数 | 统计对象 |
| --- | --- |
| `-N`、`--nodes` | 节点数量 |
| `-n`、`--ntasks` | 总任务数量 |
| `-c`、`--cpus-per-task` | 每个任务的 cpu 数量 |

大小写有区别：`-N`和`-n`不是同一个参数。slurm 中的 cpu 资源单位还取决于集群如何配置物理核心与硬件线程，不能一概把1 cpu 等同于一颗处理器芯片，或始终等同于一个物理核心。

### 一台机器启动四份程序

```text
srun -N 1 -n 4 -c 1 hostname
```

这表示使用一台节点，启动4个任务，每个任务获得1 cpu。本例假定节点资源足够，分区允许这种请求。

假想输出：

```text
node02
node02
node02
node02
```

出现四行，是因为启动了四份`hostname`。不是一份程序突然知道自己应该打印四遍，也不是使用了四台机器。

如果把`hostname`换成没有区分输入的`python count.py`，就可能让四份进程都统计同一个文件。是否需要这么做、如何分工，要由脚本和程序逻辑决定。

### 一份程序申请四个 cpu

```text
srun -N 1 -n 1 -c 4 python count.py
```

这次只有一个 python 任务，但为它申请4 cpu。资源层面与上一例都是4 cpu 的简单目标，启动形态完全不同：上一例4份进程，这一例1份进程。

如果程序只按顺序读取日志、没有使用多线程或多进程，它仍可能主要利用一个 cpu。**资源申请提供使用条件，不会自动改写程序。**

多线程是一个进程内部可以并发工作的执行单元；多进程是启动多份程序实例。具体怎样实现是程序自身的设计，这里重点区分资源申请与程序并行，不展开 python 并行编程。

### sbatch 中的-n 不是“复制脚本几份”

假设脚本写了：

```text
#SBATCH --nodes=1
#SBATCH --ntasks=4
#SBATCH --cpus-per-task=1

python count.py
```

slurm 按作业要求分配资源，但批处理脚本仍只启动一份。直接写的 python 命令通常也只执行一份，不会仅因`--ntasks=4`自动复制四次。

如果要明确启动四个受管理任务，可以在这些已经解释的参数下写：

```text
srun -n 4 -c 1 python count.py
```

但这仍只解决“启动四份”的问题，不解决“每份处理不同数据”。第14、16章会用明确编号来展示分工。

### 总量可以怎样初步估计

在这一节这些简单例子中，可把总 cpu 目标先理解为任务数乘以每任务 cpu 数：4×1与1×4都等于4。实际分配还受节点拓扑、整核心分配和站点策略影响，未必精确等于一个简单乘积。

`-n`是作业的总任务数，不是每个节点都启动这么多。申请两个节点、四个任务，不能直接读成每节点四个任务。若需要明确每节点放多少任务，还要使用相应放置要求，并确认组合可满足。

### 为什么不总是多申请一点

更多资源可能让匹配更难、等待更长，也可能在程序没有能力使用时闲置。slurm 负责按照请求安排，不能替用户证明请求是最合适的。

这一节要记住：**-N 数机器，-n 数任务进程，-c 数每个任务的 cpu；申请和利用是两个问题。** 下一节补上内存、gpu 和时间。

参考：[cpu 管理指南](https://slurm.schedmd.com/cpu_management.html)、[srun 参数](https://slurm.schedmd.com/srun.html)。

## 11. 内存、gpu 与运行时限

### cpu 之外，还有哪些资源要求

cpu 决定可以安排多少计算执行资源，**内存**用于程序运行时保存数据；**gpu**是一类适合特定并行计算的处理设备，程序需要相应的软件支持才能使用；**运行时限**是这次作业被允许占用资源的最长时间。

这三项与 cpu 数量不是同一个维度。例如，普通日志统计可能只需一个 cpu，却需要较大内存；模型训练可能同时需要 cpu、系统内存和 gpu。

### --mem 按节点申请系统内存

```text
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=4G
```

这里`--mem=4G`表示每个分配节点请求4g 系统内存。这一节用 g 作常见写法；slurm 的内存单位按其手册的二进制单位规则解释，并不是 cpu 个数。

如果申请两台节点，同样的`--mem=4G`是每台4g，不是两台合起来4g。两台机器的内存也不会因此变成一个普通进程可以直接使用的统一8g 空间。

有些集群支持按 cpu 或按 gpu 请求系统内存。它们与按节点的`--mem`是不同表达方式，不能为了“保险”随意同时叠加。初学时先把按节点这一种常见方式读准。

申请值是否被严格限制，还取决于资源选择与内存约束配置。有些集群使用操作系统的资源限制机制来执行内存上限。程序超过限制时，可能被系统终止并记录内存不足；不能无条件断言每个集群超1字节都会立即结束。

### gpu 资源需要事先被管理员登记

slurm 用\*\*通用资源（gres）\*\*表示 gpu 等额外资源。这里把 gres 理解为“slurm 已经登记、可以计数并参与分配的资源”。有 gpu 硬件不等于 slurm 已正确配置了它。

一个常见片段是：

```text
#SBATCH --partition=gpu
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=4
#SBATCH --mem=16G
#SBATCH --gres=gpu:1
#SBATCH --time=01:00:00
```

在这个示例中，管理员已建立名为`gpu`的分区并登记 gpu，用户也有使用权限。`--gres=gpu:1`请求每个节点1份 gpu 资源。因为只申请一个节点，这里总计是一张 gpu。

`--mem=16G`仍是系统内存，**不是显卡内存（显存）**。申请一张 gpu 也不保证程序使用它；程序必须具备 gpu 计算能力及所需依赖。

另一种写法`--gpus=1`表示作业总计请求1张 gpu。它属于 gpu 专用选项，需要相应的`select/cons_tres`资源选择配置；“资源选择配置”就是管理员决定 slurm 如何计量与分配资源的机制。不能把它和按节点的`--gres=gpu:1`在所有多节点场景下视为等价。

### 时间不是排队倒计时

```text
#SBATCH --time=00:30:00
```

表示运行时限30分钟。提交后等待两小时才开始运行，并不表示这30分钟已经被排队消耗掉。

时限参与调度判断：系统需要知道这份资源可能被占用多久，才能合理安排其他作业。真实到达时限后，作业通常会按 slurm 配置进入终止过程。它不会自动给程序加上保存中间结果、断点恢复的能力。

因此“时限到了以后明天自动接着算”不能由`--time`推导出来。是否能续算，取决于程序和管理员另行配置的机制。

### 怎样同时读懂一份请求

假设申请1节点、1任务、4 cpu、16g 内存、1 gpu 和1小时，正确理解是：希望在一台满足条件的节点中，运行一份能使用这些资源的程序，最长运行1小时。

它没有承诺马上开始，也没有承诺一定使用满 cpu 或 gpu；更不会自动把输入文件搬到这台节点。

这一节要记住：**内存、gpu 和时间都需要分别表达；资源含义、版本支持与集群配置前提必须一起看。** 下一节把等待与失败信息整理成一条观察路径。

参考：[内存与时间参数](https://slurm.schedmd.com/sbatch.html)、[gpu 和 gres](https://slurm.schedmd.com/gres.html)。

## 12. 状态、排队原因与失败原因

### 三种信息，不要混在一起

**状态**回答作业处于哪个阶段；**原因**解释当前为什么不能开始，或为什么结束；**程序日志**记录应用自己报告的事情。

例如，“作业等待”是状态，“所需资源暂不可用”是原因，“文件无法打开”是程序日志。只有把它们分开，才不会看到一句报错就误以为整个调度系统坏了。

### 先顺着正常过程看

| 常见状态 | 直白解释 |
| --- | --- |
| `PENDING` / `PD` | 等待开始 |
| `RUNNING` / `R` | 已获得资源并在执行 |
| `COMPLETING` / `CG` | 程序结束或被终止后，仍在清理 |
| `COMPLETED` / `CD` | slurm 记录为成功结束 |

`COMPLETING`与`COMPLETED`拼写相似，但一个是“还在完成清理”，另一个是“已完成”。清理期间可能仍有资源或步骤相关处理，不能把它当作所有事情都已经结束。

slurm 内部还会把基础状态与附加标志组合起来，命令通常显示其中一个面向用户的名称。初学时先理解常见含义，不必把所有内部标志都背下来。

### 常见结束状态

| 状态 | 主要含义 |
| --- | --- |
| `FAILED` | 非零退出或其他失败条件 |
| `CANCELLED` | 用户或管理员取消 |
| `TIMEOUT` | 达到运行时限 |
| `OUT_OF_MEMORY` | 遇到内存不足错误 |
| `NODE_FAIL` | 节点故障导致作业结束 |

这些状态指出的是不同层面的事情。`NODE_FAIL`不意味着 python 语法一定有错；`FAILED`也不一定说明机器宕机。具体原因要结合步骤、退出码和输出。

### 等待原因并非完整诊断报告

再次看5203：

```text
ST TIME NODES NODELIST(REASON)
PD 0:00 1     (Resources)
```

它正在等待，原因指向所请求资源暂不可用。以后可能变成`Priority`，表示有应优先考虑的作业，也可能出现限额相关原因。

显示出来的常常是某次调度尝试遇到的原因，并非系统已经穷举了全部阻碍。一个作业同时受资源和策略影响时，单行信息不足以把其他条件都排除。

### 用已经学过的命令观察

对于仍在队列中的作业：

```text
squeue --jobs=5203
scontrol show job 5203
```

前者看概况，后者看当前详情。对于结束后的记录：

```text
sacct --jobs=5203 --format=JobID,State,ExitCode
```

若示例显示`FAILED`、`1:0`，再看到错误文件里有：

```text
FileNotFoundError: ... 'input.log'
```

可以理解为 python 启动后，没有在预期位置打开输入文件。这个例子说明应用输入失败；它不能直接证明资源调度失败。

如果状态是`TIMEOUT`，重点是作业达到了允许的运行时限。若是`OUT_OF_MEMORY`，就关注内存需求与实际限制，但不能仅依据一个截断日志断定完整根因。

### 成功也有两个层次

slurm 记录的成功主要是程序或脚本按其退出状态结束。业务成功还要看程序是否处理了预期输入、产生正确结果。比如统计了错误文件但返回0，slurm 无法知道你原本想统计另一个文件。

因此最可靠的阅读顺序是：先辨阶段，再看原因与退出码，最后理解程序日志。这里是在学习怎样解读信息，不要求独立排错或做环境操作验收。

这一节要记住：**状态、原因、日志各有职责，不能互相代替；已结束与已成功也不是同一个判断。** 下一节解释规则如何影响谁先运行。

参考：[状态代码](https://slurm.schedmd.com/job_state_codes.html)、[原因代码](https://slurm.schedmd.com/job_reason_codes.html)。

## 13. 分区规则、优先级、qos 与限额

### 从“有空闲机器，为什么还要等”出发

资源是否空闲只是一个条件。slurm 还需要判断这个作业是否有资格使用、是否超过限制，以及在当前竞争中应该按什么顺序被考虑。

可以先按三层理解：**能不能用这些资源，当前允许用多少，满足条件后谁先被安排。** 真实调度会把这些条件一起考虑，这三层只是帮助阅读，不是内部实现的固定串行代码。

### 分区规定可选范围和规则

例如，一个假想`short`分区只允许短任务，最长运行30分钟；`cpu`允许较长的通用计算；`gpu`包含 gpu 节点并限制可使用的用户。

`--partition=gpu`只表达希望使用这个分区，不会给用户自动授予权限。相似地，把时间写成两小时，也不能自动越过一个30分钟的分区上限。

某些不合法请求会在提交阶段被拒绝，另一些限制会表现为等待，具体由配置决定。不能把“超限一定只排队”当作统一规则。

### 优先级不是固定的提交顺序

slurm 可使用多因素优先级：把等待时间、资源使用历史、分区、qos 等因素按管理员设置组合。各因素有没有影响、影响多大，都由站点决定。

\*\*公平共享（fair-share）\*\*可以直白理解为：参考用户或团队已经消耗的资源，与它应享有的份额之间的关系，影响后续安排。它不等于“每个人在任何时刻获得完全相同数量的机器”。

假设两个团队都允许使用同一分区，近期一个团队已经使用较多资源，另一个使用较少。在启用相应策略时，后者的新作业可能获得不同的优先考虑程度。这里只说明政策动机，不给出适用于所有集群的计算公式。

优先级也不是唯一排序条件。不同分区层级、预留资源和其他政策都会影响评估，所以不能把所有作业的一个数字跨范围简单比较。

### qos 是什么

\*\*qos（服务质量策略）\*\*是管理员定义的一组作业待遇和限制。它可影响优先级、资源上限，以及在启用相应机制时对其他作业的抢占。抢占是指让某些正在运行的作业让出资源，具体终止、暂停或重新排队方式取决于配置。

普通用户可能在脚本中请求：

```text
#SBATCH --qos=normal
```

`normal`只是本例中已获授权的策略名称。它不是通用口令，也不是用户可以随意把名字改成`high`就提升权限。

### 同时运行数与已提交数不是同一回事

假想某用户最多同时运行2份作业，最多保有10份等待或运行的作业。用户已经有2份运行时，新增第3份可能被接收但等待；如果等待加运行已经10份，继续提交可能被拒绝。

限制还可能按团队累计 cpu、内存、gpu 或其他资源量计算。它与“单个作业最多申请多少”也不同：单份请求合法，所有作业合计仍可能超过用户或团队上限。

slurm 中用于统计项目或团队资源的 account 也不等于 linux 登录用户名。二者可能名称相似，但一个侧重资源归属，一个侧重操作系统身份。

### 为什么后提交的小作业可能先运行

\*\*回填（backfill）\*\*是一种利用时间空隙的调度方式：在不推迟较高优先级作业预计开始时间的条件下，先安排合适的小作业。

假设大作业 a 需要几台节点一起空出来，预计20分钟后具备条件；小作业 b 只需其中目前空闲的一部分资源，并承诺5分钟内结束。在策略允许且不会影响 a 的条件下，b 可能先运行。

这解释了“后提交却先开始”不一定违背优先级。也说明合理的运行时限有意义：调度器需要知道这个空隙能否容纳作业。

这一节要记住：**分区界定范围，限额约束用量，优先级影响顺序，qos 提供一组政策；实际运行还要资源匹配。** 下一节看一批相似任务怎样高效表达。

参考：[多因素优先级](https://slurm.schedmd.com/priority_multifactor.html)、[qos](https://slurm.schedmd.com/qos.html)、[资源限额](https://slurm.schedmd.com/resource_limits.html)、[回填调度](https://slurm.schedmd.com/sched_config.html)。

## 14. 作业数组与并发上限

### 一份脚本处理五个独立输入

假设有`input-1.log`到`input-5.log`，每个文件都需要用同一个程序统计行数，五次运行互不依赖、资源需求相似。

\*\*作业数组（job array）\*\*让用户用一次提交表达一批相似作业。每个数组元素都有一个编号，通常各自运行一份脚本、拥有自己的状态与输出。这里的元素不是`--ntasks`中单个作业内的进程：数组是多份相似作业的集合，任务是某份作业内启动的程序。

### 先读懂最容易混淆的一行

```text
#SBATCH --array=1-5%2
```

把它拆成两个独立问题：

- `1-5`：这批有编号1、2、3、4、5，共五个元素。
- `%2`：这批最多同时运行两个元素。

**5决定总份数，2决定同时在做的上限。** `%2`不是每隔两个编号选一个，不是只运行两个，也不是一定分成固定的“1和2、3和4、5”三组。

### 用两个服务窗口理解并发上限

可以想成5个人等待办事，最多开2个服务窗口。只要有窗口空出来，就可能接待下一个人；不是必须等当前两个人都办完，下一组才一起进入。

下面是为解释补位机制而构造的顺序，**真实启动顺序不保证按编号递增**：

| 示例时刻 | 正在运行的元素 |
| --- | --- |
| 开始 | 1、2 |
| 2先结束 | 1、3 |
| 1再结束 | 3、4 |
| 4再结束 | 3、5 |
| 3结束 | 5 |

任何时刻都没有超过两个，但总共处理了五个。若资源只能安排一个，或其他策略暂时阻止启动，也可能只有一个甚至零个运行；`%2`是上限，不是保证值。

### 脚本怎样知道当前处理哪个文件

slurm 为每个数组元素提供环境变量`SLURM_ARRAY_TASK_ID`，其值就是这个元素的编号。环境变量是一组由运行环境提供给程序的“名字与值”。

在 shell 中，`${SLURM_ARRAY_TASK_ID}`表示取出这个值。例如编号3时：

```text
python count_file.py "input-${SLURM_ARRAY_TASK_ID}.log"
```

会把文件名`input-3.log`交给 python 程序。引号使整个展开后的文件名作为一个参数传入。

程序`count_file.py`：

```text
import sys

path = sys.argv[1]
with open(path, encoding="utf-8") as f:
    lines = sum(1 for _ in f)

print(f"{path}: {lines}")
```

`sys.argv[1]`是脚本名之后的第一个命令行参数。本例中就是输入文件名。程序仍只统计一个文件，slurm 用不同编号分别启动它。

### 完整数组脚本

```text
#!/bin/bash
#SBATCH --job-name=count
#SBATCH --partition=cpu
#SBATCH --array=1-5%2
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=2G
#SBATCH --time=00:10:00
#SBATCH --output=count-%A_%a.out
#SBATCH --error=count-%A_%a.err

python count_file.py "input-${SLURM_ARRAY_TASK_ID}.log"
```

前提仍是程序和五个输入文件对执行节点可见，用户从这些文件所在的示例工作目录提交。资源选项**作用于每个数组元素**；不是五份作业共用一份2g 内存申请。

`%A`替换数组的主作业号，`%a`替换数组元素编号。若主号为5400，元素3的输出文件就是`count-5400_3.out`。与 shell 变量不同，这些占位符由 slurm 处理。

### 怎样观察这些元素

```text
squeue --array --jobs=5400
```

`--array`要求尽量逐元素显示，`--jobs`限定这批作业。示例中可能看到`5400_1`运行、`5400_2`等待等记录；默认列表有时会把等待元素压缩成编号范围。

并发限制生效时，等待原因可能指向数组运行数量上限，也可能仍是资源或其他政策。各元素结束时间、启动顺序和内部作业号之间都不应被当成严格编号顺序。

这一节要记住：**数组编号决定每份做什么，并发上限决定最多同时做几份；数组不自动拆分输入，分工由编号与程序约定完成。** 下一节给有先后关系的作业设置依赖。

参考：[作业数组官方指南](https://slurm.schedmd.com/job_array.html)、[squeue 数组显示](https://slurm.schedmd.com/squeue.html)。

## 15. 作业依赖——前一个成功后，再运行下一个

### 需要表达的是启动条件

有时两个任务不能同时开始。例如，a 先清理日志并写出`clean.log`，b 再统计这个结果。如果 a 还没写完，b 就开始读取，会得到缺失或不完整的输入。

\*\*作业依赖（dependency）\*\*把某个作业的启动条件关联到另一个作业的结束状态。它不是把两个脚本合成一份，也不意味着两个作业会分配到相同节点。

### 先看成功依赖 afterok

普通用户在登录节点先提交 a：

```text
sbatch prepare.sbatch
```

假想回应：

```text
Submitted batch job 5501
```

再提交 b：

```text
sbatch --dependency=afterok:5501 summarize.sbatch
```

`--dependency`表示设置依赖。`afterok:5501`表示5501成功结束后，b 才满足这项启动条件。这里`ok`对应 slurm 记录的成功结束，通常需要退出码为0。

b 也会立即获得自己的作业号，例如5502，但先等待依赖。它的查询可能显示：

```text
JOBID ST NODELIST(REASON)
5502  PD (Dependency)
```

这不是提交失败，而是已经提交、尚未满足开始条件。

### 为什么不是等 a 结束以后再手动提交 b

把依赖交给 slurm 后，用户不必一直观察 a 再抓时机提交 b。b 可以预先排入系统，由 slurm 在依赖满足以后参加正常调度。

注意最后六个字：**参加正常调度**。a 成功以后，b 仍可能受资源、优先级和限额影响。依赖放行不等于预订了下一秒的机器。

### a 失败时会发生什么

如果5501失败或被取消，`afterok`条件不会因为“它总算结束了”而满足。b 可能继续等待并显示无法满足依赖等相关原因；某些配置会取消这种无效依赖作业。

不要把默认行为绝对化为“b 一定永远保留”，也不要假设重新提交一个新的 a 会自动替换旧编号。新的 a 有新作业号，原先 b 依赖的仍是5501。

### afterany 表示另一种意图

```text
sbatch --dependency=afterany:5501 collect.sbatch
```

`afterany`只要求前置作业已经结束，不要求成功。它适合无论 a 成败都要做的后续处理，例如整理运行日志。

| 依赖类型 | 放行条件 |
| --- | --- |
| `afterok` | 前置作业成功结束 |
| `afterany` | 前置作业结束，成功失败均可 |

不能为了让 b 尽快开始，就把需要正确输入的场景随意改成`afterany`。那会改变业务逻辑：前一步失败也允许继续。

### 两个必要边界

第一，依赖记录不搬运数据。a 的结果必须存放在 b 能读取的位置；即使依赖完全正确，文件不可见或权限不对仍会失败。

第二，成功依据仍是 slurm 看到的作业状态。若 a 脚本把内部错误掩盖，最后却返回0，b 可能被放行。第9节讲的退出码与业务正确性的区别，在这里尤其重要。

另一个时间条件是：依赖作业号不能随意引用早已从控制服务记录中清除的历史作业。官方对相关依赖有有效作业记录窗口要求，所以本例采用在 a 仍然活动时提交 b 的常见情况。

这一节要记住：**依赖管理开始条件，不保证立即运行，也不保证业务结果正确；afterok 与 afterany 表达不同要求。** 下一节解释一个作业如何使用多台机器。

参考：[sbatch 依赖参数](https://slurm.schedmd.com/sbatch.html#OPT_dependency)、[作业退出码](https://slurm.schedmd.com/job_exit_code.html)。

## 16. 一个作业怎样使用两台机器

### 先把三个层次拆开

多节点作业是一次作业使用多个计算节点。要让它有意义，需要分清：**slurm 分配多台机器，启动工具把程序放上去，程序本身决定各份怎样分工或通信。**

只完成第一层，不会自动完成后两层。尤其是普通 python 程序，不会因为申请两台机器就变成分布式程序。

### 两节点、每节点一个任务

先看已经能理解的`hostname`：

```text
srun -N 2 -n 2 --ntasks-per-node=1 -c 1 hostname
```

`-N 2`请求两节点；`-n 2`是总共两个任务；`--ntasks-per-node=1`在这里明确每节点放一个；`-c 1`是每任务一个 cpu。该组合假设分区至少有两台合适且获准使用的节点。

假想输出：

```text
node01
node02
```

行的先后顺序不保证。出现两个名字，说明本例两份程序分别被放到两节点，不表示这两份程序已经交换了数据。

### 批处理脚本仍然只启动一份

```text
#!/bin/bash
#SBATCH --nodes=2
#SBATCH --ntasks=2
#SBATCH --ntasks-per-node=1
#SBATCH --cpus-per-task=1
#SBATCH --time=00:10:00

srun -N 2 -n 2 --ntasks-per-node=1 -c 1 hostname
```

slurm 先在分配中的一个节点启动批处理脚本，再由脚本中的`srun`组织两个任务到相应节点。若脚本只直接写`python count.py`，不会自动在两节点各运行一次。

### 程序怎样知道自己是哪一份

`SLURM_PROCID`是 slurm 为通过`srun`启动的任务提供的编号，通常从0开始。它与数组编号不同：这里是**同一个步骤内的任务编号**。

假设两个任务分别处理`part-0.log`和`part-1.log`：

```text
import os
import socket

rank = int(os.environ["SLURM_PROCID"])
path = f"part-{rank}.log"

with open(path, encoding="utf-8") as f:
    lines = sum(1 for _ in f)

print(f"task={rank} host={socket.gethostname()}")
print(f"file={path} lines={lines}")
```

`os.environ`读取环境变量；`int`把编号文本转换成整数；`socket.gethostname()`取得当前机器名。程序根据编号拼出不同输入文件名，分工由这段逻辑完成。

对应启动可以写成：

```text
srun -N 2 -n 2 --ntasks-per-node=1 -c 1 python count_parts.py
```

两个任务都必须能找到脚本和各自输入。例如采用已配置的共享文件系统，或者管理员与工作流事先安排了文件分发。slurm 不会从文件名推断自己应该替程序拆分数据。

这两份计算相互独立，例子尚未实现跨节点合并总数。输出可能交错；正式结果文件通常也需要按任务区分，避免多个进程覆盖同一个文件。

### 如果程序之间需要互相说话

**mpi**是一套让多个程序进程交换消息的标准接口，常见于科学计算。它解决的是进程怎样通信、协调，并不等于 slurm 调度器本身。

支持 mpi 的程序与相应运行库、slurm 启动插件需要兼容。不同集群可能有不同启动方式，不能把一条带有特定 mpi 参数的命令当作普遍模板。这里先解释分工：slurm 安排资源并参与启动，通信库与程序处理进程间消息。

### 多台机器的边界

第一，内存通常是各节点独立的。节点 a 的普通 python 进程不能因为同时申请了节点 b，就把 b 的内存当作本地内存直接使用。

第二，多节点会带来通信与数据移动成本。如果任务本来很小，分布到两台机器反而可能更慢。

第三，如果任务只是大量互不依赖的文件处理，作业数组也可能是更自然的表达；如果必须在同一资源分配下协调多进程，多节点作业才更贴合。二者不是按“哪个名字听起来更高级”选择。

这一节要记住：**多节点是资源布局，多任务是启动布局，并行算法是程序设计；三者需要互相配合。** 下一节用单节点结构理解安装中的主要配置。

参考：[cpu 管理](https://slurm.schedmd.com/cpu_management.html)、[srun 环境变量与参数](https://slurm.schedmd.com/srun.html)、[mpi 指南](https://slurm.schedmd.com/mpi_guide.html)。

## 17. 单节点安装概览与 munge 答疑

### 一台机器也可以有控制和计算两种角色

单节点 slurm 不表示只有一个程序。它表示控制服务、计算服务与提交入口可以放在同一台机器上。

假设主机名是`node01`：`slurmctld`维护全局资源与作业；`slurmd`承担这台机器的执行管理；具体步骤运行时产生相应的`slurmstepd`；用户使用已经配置好的 slurm 命令提交和查询。

即使所有角色共用一台机器，提交、等待、分配、执行、结束的逻辑依然存在。两个作业的总需求超过机器容量时，仍可能排队。单节点适合理解结构、开发验证或管理一台共享计算服务器，但没有多节点容量，也不提供控制服务故障切换。

### 安装的大致顺序

这里讲安装中各项工作的关系，不给出完整部署手册。管理员通常按以下依赖组织工作：

1. 确定主机名、服务账号、业务用户以及时间设置。
2. 准备身份认证机制；这一节选择 munge。
3. 安装匹配版本、带所需认证支持的 slurm 软件。
4. 编写集群配置，描述控制服务、节点与分区。
5. 准备服务的状态、日志与运行目录，设置合适权限。
6. 先启动认证服务，再启动控制与计算服务。

软件包名、配置目录、服务文件和默认值随发行版、软件来源与版本变化。不能把一个发行版的几条包管理命令当作所有 slurm 集群的安装方式。

### slurm.conf 在描述什么

`slurm.conf`是 slurm 的主要配置文件。下面是**仅解释字段关系的片段，不是可直接启动的完整配置**：

```text
ClusterName=reading-demo
SlurmctldHost=node01
SlurmUser=slurm

AuthType=auth/munge
CredType=cred/munge

NodeName=node01 CPUs=4 RealMemory=7800 State=UNKNOWN
PartitionName=cpu Nodes=node01 Default=YES MaxTime=01:00:00 State=UP
```

`ClusterName`是集群标识；`SlurmctldHost`指出控制服务位置；`SlurmUser`是控制服务使用的专用账号，不是所有作业都变成这个用户执行。

`NodeName`定义计算节点；`CPUs`是配置给 slurm 管理的 cpu 数量；`RealMemory`是配置的可用内存数量，按该字段规定的 mb 单位解释；`State=UNKNOWN`表示初始未知，节点注册后由实际状态更新。4与7800都是示例数字，不能照抄成真实机器规格。

`PartitionName`定义分区；`Nodes`列出成员；`Default=YES`设为默认分区；`MaxTime`限制最长运行时间；`State=UP`表示分区开放相应调度。服务状态目录和其他运行设置仍需另行配置。

接下来先理解认证，再解释这两行设置。

### munge 究竟是什么：从防伪工牌理解

当用户发出“请提交这个作业”的请求，接收方不能仅因为消息里写着`alice`就相信身份。**认证**就是核对请求中的身份是否可信。

munge 是一套用于生成和验证身份凭证的服务。**凭证**是一段经过密码学保护、带有身份和有效期等信息的数据。它可以类比成临时的防伪工牌。

这里不能把类比理解成“用户自己填写工牌姓名”。在典型本机使用中，munge 后台服务通过操作系统识别连接进程的身份，以相应用户编号生成凭证；普通用户不能随意要求它把自己写成另一个用户。

一次 slurm 请求可以这样理解：

1. 用户命令借助本机 munge 服务得到身份凭证。
2. 请求把凭证带给对端 slurm 组件。
3. 对端借助它的 munge 服务验证凭证，取得可认证的用户、用户组信息。
4. slurm 再检查这个用户是否可以使用相应分区、是否超限，并处理作业。

**munge 确认是谁，slurm 规则决定能做什么。** 认证通过不等于马上获得资源，更不意味着拥有管理员权限。

### 三个相近名字

| 名字 | 作用 |
| --- | --- |
| `munged` | 后台服务，生成与验证凭证 |
| `munge` | 用于生成凭证的命令 |
| `unmunge` | 用于验证并显示凭证内容的命令 |

slurm 通过相应运行库与服务配合。用户平时仍然输入`sbatch`，不需要每次先手工制作凭证。

`AuthType=auth/munge`选择 munge 请求认证模块。`auth/munge`是模块标识，不是网址，也不是要创建的文件路径。

`CredType=cred/munge`选择用于作业启动等内部凭据的对应机制。它与“请求者是谁”的认证有关联但职责不同：内部凭据还帮助执行侧核验作业步骤获准使用相应节点资源。不要把两项都简化成用户登录密码配置。

### 安装：先明确示例环境

下面以 ubuntu 24.04、systemd 管理服务为例。所有命令仅供读懂含义，属于管理员工作，不要求执行。

```text
sudo apt update
sudo apt install munge
```

`sudo`表示以管理员权限运行；`apt update`刷新软件包索引；`apt install munge`安装该软件包。应使用发行版提供的已更新包，而不是固定某个陈旧版本。

若需要自行构建支持 munge 的 slurm，还涉及开发文件，例如 ubuntu 的`libmunge-dev`。它用于构建依赖，不是要求每个普通用户都安装开发环境。使用现成 slurm 包时，重点是包本身是否具有所需认证支持。

### 密钥怎样让多台机器相互认可

密钥是保护凭证的共同秘密，常见位置：

```text
/etc/munge/munge.key
```

同一认证范围中的相关节点要使用**同一份密钥内容**。不是文件名相同就行，也不是每台机器各自生成一份。

单节点只有一台机器，本地服务使用这份密钥；扩展到多节点时，把同一份密钥安全分发给控制、计算、提交入口，以及需要参加该认证的记账服务节点。

普通用户不应读取密钥；拥有该共同秘密的机器处于同一信任范围。munge 不是让互不信任的任意服务器仅靠一个用户名就安全加入的机制。

对于**尚未初始化的新环境、并且确认没有应保留的密钥**，munge 官方示例提供：

```text
sudo -u munge /usr/sbin/mungekey --verbose
```

`sudo -u munge`表示以服务账号`munge`执行；`mungekey`生成密钥；`--verbose`显示操作信息。安装包可能已经初始化密钥，命令路径也随版本变化，不能看到认证错误就重新生成一份。

### “怎样复制过去”与 ssh 的关系

可以使用 ssh 加密连接分发，`scp`是常见文件复制工具。这里仅展示已获授权管理员使用目标 root 账号、且目标是允许安装这份密钥的新节点的情况：

```text
sudo scp /etc/munge/munge.key \
  root@node02:/etc/munge/munge.key
```

左侧是源文件；`root@node02`是目标机器及登录账号；冒号后面是目标路径；行末反斜杠表示同一条命令换行继续。

这不是要求开放 root 远程登录。若站点禁止，就采用已有的管理员账号和提权流程。目标文件若存在，复制可能覆盖它，因此本例不能直接用于运行中集群的换密钥操作。连接前需要确认目标机器身份，不能盲目信任首次连接提示。

文件分发后，管理员在相关节点设置所有者和权限：

```text
sudo chown munge:munge /etc/munge/munge.key
sudo chmod 400 /etc/munge/munge.key
```

`chown`指定文件属于 munge 用户和组；`400`表示所有者可读，其他普通用户没有读写权限。slurm 认证示例采用0400；munge 安装指南也给出0600，即所有者可读写。两种说明的核心一致：服务账号拥有文件，不向其他用户暴露密钥，相关目录权限也必须满足要求。

**ssh 负责这一次安全复制；munge 负责随后 slurm 请求的身份凭证。** 正常提交作业不需要每次通过 ssh 复制密钥，也不等于每次通过 ssh 登录计算节点执行。

### 启动服务与观察凭证

在密钥和目录就绪的新环境中，管理员可以设置服务开机启动并立即启动：

```text
sudo systemctl enable --now munge
```

`systemctl`是 systemd 的服务管理命令；`enable`启用开机启动，`--now`同时立即启动。`munge`是服务单元名，实际运行的后台程序通常是`munged`。

下面的例子只是解释认证链路：

```text
munge -n | unmunge
```

`munge -n`生成没有附加业务数据的凭证；`|`把左侧输出作为右侧输入；`unmunge`验证它。假想成功输出包含：

```text
STATUS: Success (0)
```

它只证明示例中的本机链路。跨节点观察可以把本机凭证交给另一节点验证：

```text
munge -n | ssh node02 unmunge
```

这里假设当前执行者已经有适当 ssh 权限；`ssh node02 unmunge`在目标机运行验证命令。本机成功不保证跨节点成功，后者还依赖共同密钥、兼容配置、账号映射与时钟。

### 用户编号、时间与 slurm 集成

**uid**是 linux 数字用户编号，**gid**是数字用户组编号。各节点上相同业务用户应保持相应编号一致。否则凭证中的1001可能在另一节点被解释成不同用户。munge 不自动同步账号，也不替管理员创建作业用户。

凭证有有效期，节点时间相差过大时，接收方可能认为凭证过期或尚未生效，所以需要时间同步。

主要认证配置就是前面两行：

```text
AuthType=auth/munge
CredType=cred/munge
```

完成其他 slurm 配置后，先运行 munge，再启动`slurmctld`与`slurmd`。在这一节控制与计算同机的布局中，管理员启动服务的示例是：

```text
sudo systemctl start slurmctld
sudo systemctl start slurmd
```

`start`只负责启动服务；开机自动启动属于另一个设置。两条命令不是全部部署步骤，前面的账号、配置和服务目录必须先准备好。多节点布局则在各自角色机器启动相应服务。

使用`slurmdbd`时，它的独立配置文件`slurmdbd.conf`中也需要对应认证设置：

```text
AuthType=auth/munge
```

这只是认证片段，数据库等其他设置仍需完成；第19节解释该服务的整体作用。

已有集群切换认证方式，需要排空相关运行作业、停止相关 slurm 服务并统一调整，再按官方要求启动；不能只改一台机器或把普通配置重载当作完整认证切换。

### 普通用户最终做什么

环境准备好以后，用户仍然提交：

```text
sbatch count.sbatch
```

用户不用读取`munge.key`，不用把密钥放入脚本，也不用每次输入`munge`。安装和密钥管理主要是管理员职责。

理解 munge 错误时，也要分层：服务连接失败关注本机服务和通信权限；凭证验证失败关注密钥与兼容性；过期提示关注有效期和时钟。它们是调查方向，不能仅凭一行错误就断言唯一原因。认证成功后，作业仍可能因资源、分区权限或限额等待。

这一节要记住：**单节点合并的是部署位置，不是组件职责；munge 核对可信身份，slurm 安排资源与执行。** 下一节把同样的结构扩展到多台机器。

参考：[管理员入门](https://slurm.schedmd.com/quickstart_admin.html)、[slurm.conf](https://slurm.schedmd.com/slurm.conf.html)、[slurm 认证](https://slurm.schedmd.com/authentication.html)、[munge 安装指南](https://github.com/dun/munge/wiki/Installation-Guide)、[ubuntu 软件包](https://packages.ubuntu.com/noble/admin/munge)、[scp 手册](https://man.openbsd.org/scp)。

## 18. 多节点安装概览

### 先有角色布局，再看安装顺序

采用一个控制节点、两个计算节点的例子：

| 主机 | 主要角色 |
| --- | --- |
| `ctl01` | 运行 slurmctld；本例也提供提交入口 |
| `node01` | 运行 slurmd，承担计算 |
| `node02` | 运行 slurmd，承担计算 |

实际集群可以另设登录节点，让用户入口与控制服务分开。这里只用三个节点便于理解，并不把用户提交固定要求在控制节点上。

与单节点相比，组件的职责没有改变。多出来的是跨机器一致性和连接条件：相同用户怎样识别、主机名怎样找到、服务怎样互相通信、程序与数据怎样可见。

### 名称与网络必须说得通

配置里写`node01`，其他相关主机就要把这个名字解析到正确地址。**名称解析**就是把主机名转换成连接用的地址，可以由 dns 或明确配置的主机映射提供。

节点之间还需要按 slurm 通信要求建立连接。不只是用户能从登录节点访问控制服务就足够；启动、状态与输出等环节涉及用户命令、控制与计算侧的连接。

端口是服务接收网络连接的编号。`slurmctld`与`slurmd`常见默认端口分别为6817和6818，但这不是完整防火墙清单：实际端口可修改，任务启动和输出相关连接也需按所选版本与集群架构处理。这里不展开网络部署手册。

### 账号、认证与时间一致性

上一章解释的共同 uid/gid 映射、时间同步和 munge 密钥，在多节点中更重要。三个节点即使都有名叫`alice`的账号，也要确认数字身份一致。

munge 应在需要参与认证的节点运行，包括提交入口、控制节点和计算节点；同一认证范围使用同一密钥。若加入记账服务，还需按其认证方式配置该节点。

业务用户、slurm 服务用户、munge 服务用户有不同用途。不要为了简化而让所有作业以 root 运行，也不要把共享 munge 密钥当作业务用户密码。

### 统一的集群描述

一个解释性的片段：

```text
ClusterName=reading-demo
SlurmctldHost=ctl01

NodeName=node01 CPUs=4 RealMemory=7800 State=UNKNOWN
NodeName=node02 CPUs=4 RealMemory=7800 State=UNKNOWN
PartitionName=cpu Nodes=node[01-02] Default=YES MaxTime=01:00:00 State=UP
```

两条节点定义分别描述两台机器；分区把它们组织在同一个逻辑资源范围中。`node[01-02]`是已经讲过的名称范围。

这仍不是完整配置，认证、服务账号、目录和资源管理机制等设置不能缺失。cpu 与内存数字必须与真实节点和管理员选择的资源单位匹配，不能仅把示例主机名改掉就当作正确配置。

集群各处需要对控制服务、节点和分区拥有一致理解。常见部署分发一致的`slurm.conf`；slurm 也有由服务提供配置的方式，但改变的是配置分发形式，不是允许每个节点随意拥有互相矛盾的定义。

### 程序文件与服务状态文件不同

`slurmctld`的状态目录保存控制状态，`slurmd`有自己的节点侧运行目录。这些目录需要预先存在并拥有正确权限；不能因为用户数据放在共享目录，就把所有服务目录也随意合并成一个公共可写目录。

另一方面，用户程序、输入和结果可能放在共享文件系统中，或者通过明确的数据分发流程放到节点。**共享文件系统**就是让多个节点看到约定的文件内容。

仅在三台机器都创建同名`/shared`目录，不代表里面的文件相同。`sbatch`传送脚本，不会自动把整个工作目录同步过去。这是理解 slurm 启动作业时必须明确的文件可见性前提。

### 多节点安装的大致顺序

先规划角色、主机名与网络；统一用户、组、时间和认证；安装兼容的 slurm 软件；准备一致配置与各自服务目录；安排用户文件可见性；按角色启动认证和 slurm 服务，使计算节点注册并报告实际资源。

控制节点不必运行计算服务，计算节点通常也不运行控制服务。与单节点“同机两个角色”相比，这里是把角色分开放置。

### 容量扩展不等于高可用

增加计算节点提高可用计算容量，但只有一个控制节点时，控制服务依然是单一管理入口。**高可用**意味着关键服务故障时有设计好的接替机制；它不是“机器多就自然具备”的属性。

同样，多节点安装完成，也不证明任何 python 程序都能跨节点并行。第16节的程序分工边界仍然成立。

这一节要记住：**多节点保持同一套职责，增加的是网络、身份、配置与数据的一致性要求；不是把单节点命令机械复制几遍。** 下一节看记账与 api 两个可选扩展服务。

参考：[管理员入门与基础设施](https://slurm.schedmd.com/quickstart_admin.html)、[集群配置](https://slurm.schedmd.com/slurm.conf.html)、[认证要求](https://slurm.schedmd.com/authentication.html)。

## 19. slurmdbd 与 slurmrestd

### 两个扩展服务，解决两类问题

核心组件已经能接受作业、分配资源并启动程序。但集群还可能需要长期保存运行历史，或者让网站、脚本和其他软件通过接口接入。

| 组件 | 主要解决的问题 |
| --- | --- |
| `slurmdbd` | 在 slurm 与记账数据库之间处理记录和相关管理 |
| `slurmrestd` | 向其他软件提供 rest api 接口 |

二者不是新的计算节点，也不替代`slurmctld`的调度职责。

### slurmdbd 与数据库是什么关系

**数据库**是保存和查询结构化记录的软件。`slurmdbd`可以理解为面向 slurm 的记账服务入口：接收相关作业信息，与后端数据库交互，支持历史查询和资源归属、限制等管理。

它不是数据库本身。常见关系是：控制服务产生作业与步骤信息，记账服务把它们写入数据库，用户通过`sacct`等命令查询。

一个解释性的控制侧配置片段：

```text
AccountingStorageType=accounting_storage/slurmdbd
AccountingStorageHost=db01
```

`AccountingStorageType`选择记账存储方式；这里通过`slurmdbd`。`AccountingStorageHost`指出该服务所在主机。`db01`是示例名，不表示它必须与数据库同机，也不表示两行就完成了部署。

记账服务还需要独立配置、数据库连接与权限、认证以及相关记录管理。记录是否存在、保留多久、哪些字段可见，仍要看实际配置。

### 历史记录能告诉什么

```text
sacct --jobs=5203 --format=JobID,State,Elapsed
```

`Elapsed`是已用运行时长，常用“时:分:秒”形式显示。简化示例：

```text
JobID      State      Elapsed
5203       COMPLETED  00:02:15
5203.batch COMPLETED  00:02:15
```

它能帮助回答作业怎样结束、运行了多久。若配置了相应采集，还能查询更多资源使用信息；但某个统计为0或空白，不一定真的从未使用，可能是该字段未采集或在当前层级不适用。

这里要再分清**分配量**与**实际利用量**。作业分到4 cpu 并运行10分钟，不表示它在这10分钟里每个 cpu 都一直忙。slurm 可以记录获批资源，也可按配置采集使用情况，二者含义不同。

记账也不等于保存业务结果。`lines=12000`的输出文件、训练模型文件或处理后的日志，仍由程序和存储安排管理。

### slurmrestd 是什么

**api**是软件之间调用功能的接口；**rest api**通常通过 http 这种网络请求方式访问，并常用 json 这种结构化文本格式组织数据。对于熟悉后端开发的读者，可以把`slurmrestd`理解为 slurm 提供的软件接入服务。

例如，一个内部作业门户可以通过它获取作业和节点信息，也可在权限允许时提交或管理作业。负责做网页、表单和用户体验的是门户程序；安装`slurmrestd`本身不会自动生成一套完整网站。

### 认证与版本为什么不能省略

api 请求仍然需要身份与权限约束。官方提供本地认证、令牌认证等方式，取决于通信方式和部署配置。**令牌**是请求携带的一种身份凭据，不等于 munge 密钥；两者不能混放在客户端代码里。

接口路径、数据结构与可用方法受 slurm api 版本及插件影响。教程不能假设任意版本的某个 json 都可以永久原样提交。

控制类接口通常关联控制服务；历史记账类接口还需要相应的记账服务与数据库支持。启用 api 不能凭空补出从未保存的历史。

### 为什么它们是可选扩展

一个小型单节点入门环境可以先理解核心调度与执行，再决定是否需要长期记账和软件接入。正式共享集群往往更需要历史、资源归属和策略管理，但具体是否部署这些组件，取决于需求与站点设计。

这一节要记住：**slurmdbd 连接历史与管理数据，slurmrestd 连接外部软件；二者扩展能力，不改变核心计算职责。** 下一节用完整作业把前面知识串起来。

参考：[记账与资源限制](https://slurm.schedmd.com/accounting.html)、[sacct](https://slurm.schedmd.com/sacct.html)、[rest api 说明](https://slurm.schedmd.com/rest.html)、[slurmrestd](https://slurm.schedmd.com/slurmrestd.html)。

## 20. 完整案例——一份日志统计作业怎样从提交走到结果

### 先把案例条件交代清楚

alice 要统计`input.log`的行数。她在登录节点使用普通用户命令，计算由`cpu`分区中的节点承担；程序只需要单节点、单任务、一个 cpu。

集群已由管理员配置好：控制与计算服务运行正常；认证可用；python 存在于计算节点；`/shared/count`中的脚本和输入对执行节点可见，用户有读写权限；记账服务已保存本例历史。

这一节不要求准备这些条件，也不会实际提交任何作业。所有输出都是为说明流程构造的示例。

### 第一步：查看资源范围

```text
sinfo --partition=cpu
```

将示例输出摘取为：

```text
PARTITION NODES STATE NODELIST
cpu*      1     idle  node01
cpu*      1     mix   node02
```

这表示分区中一台空闲、一台部分 cpu 资源已分配。它帮助理解候选资源，但不能保证 alice 立即获批；最终仍要结合她的请求和集群规则。

### 第二步：读懂程序和提交脚本

程序`count.py`：

```text
with open("input.log", encoding="utf-8") as f:
    lines = sum(1 for _ in f)

print(f"lines={lines}")
```

业务逻辑仍是读取文件、累计行数、输出数字。没有复杂依赖，也不因资源申请而自动并行。

提交脚本`count.sbatch`：

```text
#!/bin/bash
#SBATCH --job-name=count
#SBATCH --partition=cpu
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=2G
#SBATCH --time=00:10:00
#SBATCH --chdir=/shared/count
#SBATCH --output=count-%j.out
#SBATCH --error=count-%j.err

srun -n 1 -c 1 python count.py
```

先补清这一节用到的`--chdir`：它指定批处理作业的工作目录，也就是相对文件名的解释起点。这里明确选择`/shared/count`，使`count.py`、`input.log`和相对输出文件名有清楚的位置；它不会创建目录或复制输入。

其余参数把请求明确写成：`cpu`分区，1节点，1任务，每任务1 cpu，每节点2g 系统内存，最长10分钟。两个输出指令把普通输出与错误输出分开。

脚本中的`srun -n 1 -c 1`在已有分配内启动一份 python 任务，并明确这一步的任务与 cpu 数量。它是最后一条命令，本例没有再用后续成功命令掩盖它的退出状态。

### 第三步：提交不等于开始

```text
sbatch count.sbatch
```

假想回应：

```text
Submitted batch job 5901
```

5901成为本次运行的查询编号。控制服务接收请求，检查用户及分区规则，建立作业记录。接收成功后`sbatch`返回，用户不必把提交终端一直当作程序现场。

### 第四步：等待调度

```text
squeue --jobs=5901
```

假想先看到：

```text
JOBID ST TIME NODES NODELIST(REASON)
5901  PD 0:00 1     (Resources)
```

作业尚未开始，time 因此是0。等待可能来自当前资源不匹配；如果原因后来变化，也不表示这是另一个作业。

### 第五步：资源分配与组件协作

当规则与资源条件满足，`slurmctld`把合适节点资源分给5901。假设最终选择`node02`，后续查询可能显示：

```text
JOBID ST TIME NODES NODELIST(REASON)
5901  R  2:15 1     node02
```

这里2分15秒是已运行时长，1是已分配节点数。节点选择取决于当前真实条件，不应从先前一次`sinfo`快照推断它永远不变。

把执行侧再串一次：节点上的`slurmd`参与落实启动；batch 步骤的`slurmstepd`管理脚本；脚本中的`srun`创建普通步骤，相关执行管理进程启动 python 并处理输出。python 读取日志、统计行数，slurm 不替它计算。

若节点采用 munge 认证，身份凭证在通信过程中由软件自动处理。alice 不需要把密钥写入作业脚本。

### 第六步：读取结果与核对结束状态

假设输入示例确实有12000行，标准输出文件`/shared/count/count-5901.out`包含：

```text
lines=12000
```

错误文件`count-5901.err`在这个构造示例中没有异常文本。空错误文件只是线索，不是独立成功证明。

再看记账记录：

```text
sacct --jobs=5901 --format=JobID,State,ExitCode
```

简化示例：

```text
JobID      State      ExitCode
5901       COMPLETED  0:0
5901.batch COMPLETED  0:0
5901.0     COMPLETED  0:0
```

整个作业、脚本步骤和普通步骤都记录为成功；输出也符合本例给出的输入条件。这些信息共同构成理解结果的依据。真实业务仍需用自己的结果规则判断，而不是一律把0:0当作答案正确。

### 换一种结果，观察主线是否还成立

如果作业一直 pd，程序可能还没执行，应该读等待原因；如果程序已启动却报输入不存在，问题在执行或数据条件，不是“还没拿到作业号”；如果 timeout，关注运行时限；如果用户取消，则不期待程序自然完成。

这些情况使用同一套对象：作业号标识运行，分区限定资源，控制服务安排，计算服务与步骤管理进程落实执行，输出和记录说明结果。理解主线后，就不必把每个命令当成互不相干的缩写背诵。

### 把命令放回同一条主线

理解 slurm，可以始终围绕一份作业追问：它请求了什么资源，何时获准，程序在哪些节点启动，怎样记录输出，最后如何释放资源。

`sinfo`看资源，`sbatch`提交说明，`squeue`观察当前状态，`srun`启动任务，`sacct`帮助理解结束后的记录。控制服务、节点服务和步骤管理进程，把这些命令连接成了一个完整过程。

资源申请不等于程序会自动并行，认证通过不等于立即获批，成功退出也不等于业务答案必然正确。把这些边界分清，阅读脚本和理解调度结果就会更有依据。

参考：[用户入门](https://slurm.schedmd.com/quickstart.html)、[sbatch](https://slurm.schedmd.com/sbatch.html)、[作业启动流程](https://slurm.schedmd.com/job_launch.html)、[sacct](https://slurm.schedmd.com/sacct.html)。

## 几个容易卡住的问题

### 为什么有 slurmd，还需要 slurmstepd

`slurmd`是节点上的常驻服务，`slurmstepd`管理某个具体步骤的进程、输出与结束。批处理脚本本身就有 batch 步骤，所以没有显式写`srun`，也不代表没有`slurmstepd`。对应解释见[第3节](#lesson-03)。

### sbatch 脚本里到底要不要写 srun

简单单节点脚本可以直接启动程序；需要把程序作为独立步骤管理，尤其需要在多个节点放置任务时，`srun`更能表达这种启动意图。它不是让普通程序自动并行的开关。对应例子见[第7节](#lesson-07)和[第16节](#lesson-16)。

### salloc 成功了，为什么 hostname 还是登录节点

获得分配和 shell 的运行位置是两回事。在没有特殊交互入口配置的常见模式中，shell 仍留在发起端；通过`srun`才把命令放到计算节点。部分站点配置会改变这种行为，所以不能只凭获批提示推断位置。见[第7节](#lesson-07)。

### --array=1-5%2是不是分成固定三批

不是。5表示总共五个元素，2表示最多同时运行两个。某一个先结束，就可以为另一个元素腾位置，不必等待固定同组成员全部结束；实际顺序还受资源与调度影响。见[第14节](#lesson-14)。

### auth/munge 是一种登录方式吗

它是 slurm 认证模块的标识。munge 通过凭证帮助核验请求身份，不替用户创建 linux 账号，也不等于 ssh 登录。普通用户提交作业时由软件自动处理凭证；服务安装与密钥管理主要由管理员完成。见[第17节](#lesson-17)。

### 为什么各节点不能各自生成 munge.key

文件名相同不代表内容相同。相关节点依赖同一份共同秘密互相核验凭证；每台各自生成会失去这个前提。ssh 可以用于安全分发这份文件，但不是每次提交作业都复制一次密钥。见[第17节](#lesson-17)。

## 命令与组件速查

### 常用命令：按问题查找

| 想了解或处理的事情 | 主要命令 |
| --- | --- |
| 分区和节点概况 | `sinfo` |
| 当前自己的作业 | `squeue --me` |
| 某个作业的当前队列信息 | `squeue --jobs=作业号` |
| 提交批处理脚本 | `sbatch 脚本名` |
| 在 slurm 管理下启动程序 | `srun … 程序` |
| 先获得一份资源分配 | `salloc …` |
| 取消自己的某个作业 | `scancel 作业号` |
| 查看当前作业详情 | `scontrol show job 作业号` |
| 查询保存的历史记账记录 | `sacct --jobs=作业号` |

表中的省略号与中文作业号是说明用占位，不是可直接执行的实际命令。具体参数、权限、记账与配置前提在各节解释。

### 组件：按职责查找

| 组件 | 职责关键词 |
| --- | --- |
| `slurmctld` | 全局状态、调度、资源分配 |
| `slurmd` | 计算节点的执行管理入口 |
| `slurmstepd` | 具体执行步骤与进程生命周期 |
| `slurmdbd` | 记账服务与数据库交互 |
| `slurmrestd` | 对外软件接口 |
| `munged` | munge 身份凭证生成与验证 |

### 四组容易混淆的区别

- **申请与执行**：请求若干 cpu，不会自动产生若干份程序；需要明确的启动方式。
- **作业与步骤**：作业提供外层资源与生命周期；步骤组织作业内的一次执行。
- **资源与利用**：获得 gpu 或多个 cpu，不表示程序已经具备相应计算能力。
- **结束与正确**：退出状态是程序报告，业务答案仍需符合输入与逻辑。

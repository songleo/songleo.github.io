把本机连接给 dots 并授权指定的本地任务后，最需要弄清楚的是：哪些事情直接和它讨论，哪些事情交给本地任务执行，以及执行到哪一步需要自己决定。

一句话理解：dots 提供云端个人 ai 助手，可以研究问题、整理材料、跟进已交代的工作，也可以把指定的本地工作交给已连接的电脑执行。dot 指其中一个助手。它使用可用的上下文和授权范围内的工具推进工作。[官方介绍](https://learn.chatgpt.com/docs/dots)

本文依据截至 2026 年 9 月 30 日的官方说明整理。下面的开发场景是用法示例，不是实际完成案例。

## 1 chat、dots 和本地 work/codex 怎么分工

对于 ai 平台后端开发工程师，比较实用的分工是：

| 入口 | 适合做什么 | 需要提供什么 |
| --- | --- | --- |
| chatgpt 的 chat | 解释概念、比较方案、讨论设计 | 问题和必要背景 |
| dots | 整理材料、写草稿、跟进任务、安排提醒，协调需要执行的工作 | 目标、资料和授权范围 |
| work/codex 任务 | 在指定环境读取文件、修改文档或代码、运行检查 | 电脑、目录、允许修改的范围和完成标准 |

work 是执行任务的工作模式；codex 更常用于仓库和开发工具相关的工作。上表是使用建议，不是功能的硬性划分。

比如准备一篇技术博客，可以先和 dots 确认读者、提纲和例子。需要参考本地文章、创建文件并验证格式时，再让它启动本地任务。这样能减少执行过程中反复改目标、重读资料和返工。

读邮件或资料也要先连接对应的应用，并且只能在已有权限内操作。“能聊天”“能读邮箱”“能访问电脑”是不同的授权。[电脑与应用连接说明](https://learn.chatgpt.com/docs/dots/computers-and-apps)

除了文字，也可以在支持的入口与 dots 实时语音交流，适合口头梳理需求或追问进度。这里的通话对象是 ai 助手，不能理解为替我拨打第三方电话或加入会议。[消息与语音说明](https://learn.chatgpt.com/docs/dots/channels)

## 2 云端电脑和本机是两个环境

dots 的云端电脑是一个可以操作浏览器、文件和终端的工作台。终端就是输入命令、运行脚本的工具。它适合网页研究、数据和文件处理、文档整理，以及验证小型代码例子。连接本机后，dots 还可以安排任务使用本机允许访问的文件、开发工具和应用。

### 云端电脑是什么配置

2026 年 9 月 30 日，对本次会话的云端执行环境做了只读检查，得到下面这份可见资源快照。配置可能随分配变化，不是官方固定规格，也不代表这些资源由单个用户独占或具有性能保证。

| 项目 | 本次环境可见结果 |
| --- | --- |
| 操作系统 | debian 13 |
| 架构 | x86_64 |
| 逻辑 cpu | 9 个，未确认型号 |
| 内存 | 约 9.7 GiB |
| 工作区容量 | 约 32 GB |
| gpu | 未发现可见的 gpu 设备 |

“未发现 gpu 设备”只说明本次环境没有看到可用设备，不能据此保证整个基础设施没有 gpu。

这台电脑用于执行浏览器、文件和脚本操作，与提供模型推理的后端服务不同。不能根据它的 cpu、内存或 gpu 可见情况，推断模型的参数规模或推理能力。这些资源也不意味着免费、无限的算力。

### 云端电脑适合做什么

比如，先让 dots 在云端整理公开技术资料、比较方案并准备文章提纲；需要参考用户现有博客风格、编辑文章并检查格式时，再交给已连接的本机执行。云端生成一个文件，不等于它已经保存在指定的本地目录。

对于 ai 平台后端开发，云端还适合这些范围较小的工作：

- 用模拟数据验证接口参数校验、重试逻辑和 json 转换，不调用真实业务接口。
- 统计用户提供的脱敏日志中的错误和耗时，帮助定位值得进一步排查的问题。
- 根据用户提供的配置，检查离线镜像、依赖和 helm values（部署参数文件）是否遗漏，不能替代目标环境的实际部署验证。
- 用一次性脚本做小实验，减少在本机 windows/wsl 中反复安装依赖带来的冲突。
- 本机关机后，继续整理公开资料和研究不依赖本地文件的问题。

比较实用的分工是：云端做资料分析和小验证，本地 codex 修改真实仓库并运行测试，开发服务器验证部署与 gpu/npu 等加速设备。这样有助于减少环境准备和维护成本，不保证节省额度。不要默认云端能访问公司内网，或能运行 docker、kubernetes 和完整离线部署。

云端电脑也不应当作有持久托管保证的服务器使用。重要成果应保存到用户指定的位置；不要假设磁盘无限、后台服务会永久运行，或所有网站和网络地址都能访问。

需要本机参与的步骤，要求这台电脑在线，并保持 chatgpt 桌面应用开启。本机关机后，云端工作仍可能继续，但需要读取本地仓库或运行本地命令的步骤会受影响。[电脑连接要求](https://learn.chatgpt.com/docs/dots/computers-and-apps)

连接电脑也不意味着所有本地 chatgpt/codex 对话自动同步，或 dots 已经知道用户正在做的全部工作。新任务仍需要相关背景；如果要接着某个已有任务做，应明确指出任务和下一步目标。[任务与上下文说明](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

因此，委派本地工作时要说清楚“在哪台电脑、哪个目录做什么”。路径不确定，就先定位并确认，不能让它猜一个看起来像项目的目录。
### 怎么让 dots 使用云端电脑

直接在 dots 对话中说明任务和执行环境即可，不需要自己连接云端终端。“在你的云端电脑上执行”指 dot 的云端环境；“在我的电脑”或“在已连接的开发电脑上执行”指本机，后者需要电脑在线、应用开启，并获得相应授权。本地任务还要提供准确目录。

比如，分析上传的脱敏日志：

```text
在你的云端电脑上，用 python 分析我上传的脱敏日志。
统计最常见的 5 类错误，说明分类规则、次数和可确认的原因。
如果字段不足或存在无法解析的记录，报告限制，不猜测。
交付统计结果、简短结论和可下载的分析脚本。
不访问本机、不连接真实业务服务。
```

验证重试机制时，要求实际运行，而不只是给一段代码：

```text
在你的云端电脑上，用 python 写并实际运行一个重试机制最小例子。
模拟前两次调用失败、第三次成功，输出每次尝试与最终结果。
说明最大尝试次数、失败处理和停止条件，区分模拟结果与真实服务行为。
只用模拟数据和标准库，不调用外部接口，不修改本机文件。
交付代码、实际运行输出和解释。
```

检查上传的 helm values 时，先交代验证边界：

```text
在你的云端电脑上，分析我上传的 helm values。
先说明缺少 chart 或 values schema（参数结构与类型约束）会限制验证。
检查能确认的明显字段冲突、格式问题和疑似缺失项，区分确定问题与待核实项。
不要把 chart 默认值或未提供的规则当成已知事实。
只分析并给出依据和建议，不连接、不修改集群，不执行部署。
```

如果希望先判断执行方式和用量，可以给上述提示词追加：“先说明执行方案；如需启动 work/codex，先告诉我，等我决定再启动。”这是用户可以自行选择的任务边界，不代表产品所有操作默认都先确认，也不代表云端执行全部免费。额度区分见第 5 节。

## 3 后端开发中可以怎样用

下面四个场景都可以从小范围开始。示例中的目录需要替换成实际路径，材料也应先确认允许交给助手处理。

### 读懂技术方案

比如学习 kubernetes 调度或容器镜像机制，先在对话里理解，再决定是否需要本地实验。普通解释不必每次都新建执行任务。

```text
解释 kubernetes 中 requests 和 limits 对调度与运行的影响。
先讲它们分别解决什么问题，再给一个后端服务的例子。
陌生概念就近解释，引用官方文档，未确认的行为明确标注。
只在当前对话说明，不启动 work，也不访问本机。
```

### 把需求变成接口验收清单

后端需求常写“支持某项能力”，实现和验收却要落到具体接口、权限和错误场景。可以先让 dots 把提供的需求整理成表，再由自己确认范围。

```text
根据我提供的需求，整理接口验收清单：
需求能力、接口、正常场景、失败场景、验收依据、待确认问题。
区分需求明确要求的内容和你的建议，不把建议写成既定需求。
只使用所给材料，不访问本机、不调用真实接口。
```

如果还需要读取本地接口定义，再单独指定仓库和文件范围。这样不会在整理需求时顺便扩大成代码审查或接口测试。

### 根据现有材料补一份使用说明

安装说明、开发环境准备和 ci 失败排查，都可以先整理已有命令和证据，帮助下一次少翻聊天记录。尚未执行的命令必须标清楚。

```text
在已连接电脑的 /path/to/project 中，读取仓库写作规则、
readme 和我指定的安装脚本，只新建 docs/setup-notes.md。
写清前置条件、操作步骤、验证方法和已知限制。
只记录现有材料支持的内容；未实测的步骤标为待验证。
不执行安装、不修改脚本、不连接测试环境、不提交或发布。
```

这里委派的是文档任务。正在本地推进的开发工作可以继续按原计划进行，不需要因为电脑已连接，就把它们全部交给 dots。

### 为一个明确的小改动执行验证

比如已确认某个 go/python 函数需要调整，可以让本地任务只处理指定模块，并运行相关检查。先确认目录里的已有改动，能避免与另一个任务改到同一文件。

```text
在已连接电脑的 /path/to/project 中完成下面这个小改动：
【填写已确认的行为、涉及模块和验收条件】。
先查看仓库规则和已有改动，保留与本任务无关的内容。
仅修改指定模块，运行相关检查，不提交、不推送、不部署。
如果发现另一个任务正在修改同一文件，先停下来说明冲突。
结束时报告修改文件、验证证据和未完成项。
```

## 4 高效委派靠一张清楚的交接卡

目标还不明确时，先在对话里讨论。方案确定后，把执行所需的信息压缩成一张交接卡；原对话可以作为补充材料，不必让新任务重新从长记录里找结论。

```text
目标：最终要得到什么结果。
执行位置：已连接的电脑名称、仓库或文件的准确路径。
来源：指定文件、资料或已经确认的方案。
范围：允许读取和修改什么，哪些内容不要触碰。
完成标准：结果应满足哪些要求，需要哪些验证证据。
停止条件：遇到路径歧义、并发冲突或需要扩大范围时先说明。
交付：报告文件路径、主要变化、检查结果和未完成项。
发布边界：仅本地保存，不提交、不推送、不部署、不对外发送。
```

可以为 dots 启动的 work 任务指定默认模型和推理强度，例如 gpt-6.1、中度推理。这只是个人设置示例，不是所有产品任务的统一默认值。任务有特殊要求时，应在开始前明确指定；模型和推理强度也不能代替清楚的目标与验收标准。

执行期间新增一个要求，最好说明它是在补充当前任务，还是要暂停并换目标。结束后检查实际文件和验证证据，不能只看“任务已完成”的状态。[结果检查说明](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

## 5 额度要按实际执行方式区分

这是最容易混淆的地方。官方 dots 文档明确区分了以下几类：[额度说明](https://learn.chatgpt.com/docs/dots#access)

| 使用方式 | 怎样理解额度 |
| --- | --- |
| 与 dot 对话 | 不计入 chatgpt 使用限额 |
| dot 发起或管理的 work/codex 任务 | 照常计入对应产品的用量，按其规则计量或计费 |
| 其他深入工作 | 方案包含深入工作额度，具体剩余量和规则看账户最新显示 |

所以，“在 dots 这里讨论一篇博客”和“让它启动本地 work，读取文章并写入博客目录”属于不同的使用方式。后者仍会占用对应额度。不能把对话不计限额，推导成所有云端或本地任务无限免费。

chat 中 gpt-6 pro 这类模型的消息上限，也要与 work/codex 的用量分开看。work/codex 的本地与云端任务可能共享对应的用量池，不是换台电脑或换入口就获得一份新额度。[work/codex 用量说明](https://learn.chatgpt.com/docs/pricing)

dot 语音时长和调用频率的具体上限，未查到明确公开数字，以账户用量和官方最新说明为准。对话不计 chatgpt 限额，也不能推出语音或深入工作没有限制。

比较合理的做法是先用对话理清方案、材料和草稿，再启动必要的执行任务，减少反复。不要为了省额度盲目搬任务。拿不准时，可以先这样问：

```text
这项请求准备直接在 dot 对话中处理，还是启动 work/codex？
会在哪个环境执行，预计涉及哪类用量？
先说明执行方式和可确认的额度规则，不启动任务；
无法确认的部分标为未知。
```

## 6 权限边界和一天的使用方式

电脑连接只是提供了一个可用的执行环境，不能理解为无限权限。可以明确要求只读、不修改、不发布；发送对外消息、付款、删除内容，以及涉及安全设置或凭据的操作，仍要遵守授权和实际权限。需要登录时使用受控登录流程，不把密码、token 或私钥贴进提示词。[权限与审批说明](https://learn.chatgpt.com/docs/dots#permissions-and-approvals)

提醒也需要明确交代时间、时区、提醒内容和通知位置，并确认它已经保存。接通语音、连接邮箱或电脑，都不等于自动创建了提醒。挂断语音也不等于停止已委派的任务。[任务与提醒说明](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

可以从这样的日常安排开始：上午用 dots 梳理今天的问题和材料；遇到概念或方案选择，先在对话里讨论；目标确定后，把必要的本地读写交给一个范围明确的 work/codex 任务；结束时查看文件、检查结果和待办，再决定是否提交或发布。

同时有多个任务时，尽量让它们处理不同文件。指定仓库只能说明工作位置，不能保证多个任务会自动协调好修改。

连接本机最有用的地方，是可以把讨论后的明确目标交给电脑执行，并拿回可检查的结果。每次把目录、范围和完成标准说清楚，才更容易用得合理、用得高效。

做 AI 平台后端，除了写 Go、Python 代码，还会碰到部署检查、前后端联调、离线包验证和回归排查。很多小动作反复出现：从聊天里找命令，切换几个终端看 Pod，把请求重新拼一遍，再从大量日志中寻找同一次失败。

结合最近两个月涉及的这些工作，本文挑选了 5 个候选工具：just、k9s、Bruno、Difftastic 和 lnav。它们分别解决一个明确问题，可以接入现有的 VS Code、终端、Git 和 Codex 工作流。

这份清单依据截至 2026 年 10 月 7 日的官方资料整理。下面是建议用法，不代表这 5 款都已安装或完成实测；也没有测量过它们能节省多少时间。示例名称、文件和环境需要按实际项目调整。

选择时主要看三点：是否对应经常重复的动作，能否复用已有文件与命令，免费部分是否足够完成这个小流程。对于已经使用 Windows 与 WSL 的开发环境，能在现有终端中完成的事情，就尽量少增加一套需要长期维护的服务。工具之间有功能重叠很正常，关键是把各自负责的步骤说清楚。

## 1 just：给重复命令一个固定入口

一个仓库里可能同时有测试命令、配置检查、打包脚本和验收脚本。任务隔几天再接着做，首先要弄清楚的经常是“上次到底怎么运行”。如果每次交给 Codex 都重新组织一组命令，执行范围也容易变化。

just 是项目命令运行器。把常用命令写进 justfile 后，可以列出入口、查看内容，再明确选择执行哪一项。官方支持参数、脚本和从项目子目录调用等用法。[官方介绍](https://just.systems/man/en/)

### 从一个检查入口开始

以已经能正常运行测试的 Go 项目为例，在项目根目录添加下面的 justfile：

```makefile
default:
    @just --list

# 运行当前 Go 模块的测试
check:
    go test ./...
```

日常使用时，先查看，再运行：

```bash
just --list
just --show check
just check
```

这里的 check 是自己定义的名字。测试范围仍由命令和项目决定，不能因为入口叫 check，就认为部署、接口和离线安装都验证了。`--list` 和 `--show` 的作用是让命令更容易发现和复核。[命令查看方式](https://just.systems/man/en/command-line-options.html)

如果项目已有验证脚本，recipe 直接调用它即可。可以逐步整理出配置检查、接口冒烟等入口，但每个入口都应写清输入、目标环境和输出位置。给 Codex 的任务也可以明确成“先查看 check 的内容，再运行并报告原始结果”。

### 平台、成本与边界

just 支持 Windows、Linux 和 macOS，采用 CC0-1.0，免费。已有 Bash 脚本时，在 WSL/Linux 中使用更容易保持一致；Windows 原生需要选好实际使用的 shell。[项目与许可证](https://github.com/casey/just)

工具本身可离线运行，但内部命令仍可能下载依赖。它也会执行任意项目命令，所以不要把部署、删除资源或推送操作藏在一个含糊的默认入口里。

just 与 Make、shell、CI 有重叠。它适合整理日常操作入口，不负责替代构建依赖或整条发布流水线。如果现有 Makefile 已经清楚、稳定，继续用就好。

## 2 k9s：连续查看集群里的问题

部署后服务没有就绪，通常要依次查看 Pod、事件、容器日志，再回到资源列表确认状态。kubectl 足够完成这些工作，不过在多个资源之间来回切换，需要不断输入查询命令。

k9s 在终端里提供 Kubernetes 资源视图，支持过滤、查看详情和日志。它适合已经习惯 SSH、MobaXterm、tmux 的工作方式。[官方项目说明](https://github.com/derailed/k9s)

### 用只读方式查看一个测试环境

先确认已有 kubeconfig 中的 context 和 namespace，再启动：

```bash
k9s --context lab -n ai-platform --readonly
```

lab 和 ai-platform 都是示例名称。进入后先确认屏幕上的目标环境，再按下面的顺序排查：

1. 在 Pod 列表中过滤目标服务。
2. 按 d 查看详情，检查事件与启动状态。
3. 按 l 查看日志，再回到列表观察变化。

例如某个服务迟迟未就绪，可以先判断线索落在镜像拉取、存储挂载、探针还是应用启动阶段，再决定下一条精确查询。不要看到重启次数增加就直接删除 Pod。[命令与快捷键](https://k9scli.io/topics/commands/)

### 平台、成本与边界

k9s 提供 Windows、Linux、macOS 二进制，采用 Apache-2.0，免费。可以放在 WSL 或已有管理机上；使用时仍然需要能访问目标 Kubernetes API，并具备相应权限。[安装与许可](https://github.com/derailed/k9s)

在不连接互联网的客户网络中，只要集群 API 可达，就能进行相应操作；“离线可用”不意味着断开集群后仍能查看实时状态。

`--readonly` 有助于避免误操作，真正的权限限制仍应由只读 RBAC 提供。RBAC 是集群中的角色访问控制。不要为了让界面显示更多内容而直接使用管理员凭据，也不要把只读开关当作安全隔离。

k9s 负责交互观察，kubectl 继续负责精确查询、导出和脚本化操作。它不会替代终端连接工具，也不必承担完整的业务流程管理。

## 3 Bruno：把联调请求保存下来

前后端联调时，一条请求可能先出现在浏览器里，再变成聊天中的 curl，最后只剩某个人终端中的历史记录。下次验证相同问题，又要重新确认地址、参数和预期响应。

Bruno 是离线优先的 API 客户端，请求集合保存在本地文本文件中，可以用 Git 管理，也能通过 CLI 回放。常规使用不要求云账号。[官方入门](https://docs.usebruno.com/introduction/getting-started)

### 先留下三个只读请求

以数据集页面联调为例，可以从项目真实接口中选择列表查询、单项详情和权限检查，组成一个 smoke 文件夹。每条请求只保留当前问题需要的断言，例如状态码、必要字段和错误结构。

最小流程是：

1. 从实际接口文档或已经确认的请求创建 collection。
2. 将环境地址提取为变量，准备 test 环境。
3. 保存无秘密的请求模板和断言，用现有 Git 管理。
4. 在 collection 根目录运行选定的请求。

```bash
bru run smoke --env test
```

smoke 和 test 是将来创建的示例名称。执行前仍要检查实际地址和请求方法，避免把会创建、删除数据的接口混入只读检查。[CLI 用法](https://docs.usebruno.com/bru-cli/run/overview)

接口回放有助于缩小问题范围。页面按钮、表单校验和完整用户操作仍由 Playwright 验证，不需要把已有 E2E 用例全部再写一遍。

### 平台、成本与边界

桌面端支持 Windows、Linux 和 macOS；CLI 可使用 Node.js 或官方容器。进入断网环境前，需要备齐运行时、依赖或镜像。[下载页面](https://www.usebruno.com/downloads)、[CLI 安装](https://docs.usebruno.com/bru-cli/installation)

核心项目采用 MIT 许可证，开源版免费。本文建议的本地请求、外部 Git 管理和 CLI 流程可以从免费部分开始；付费版本另有集成、管理与支持能力，没有必要为这个小流程先买订阅。[开源仓库](https://github.com/usebruno/bruno)、[版本与价格](https://www.usebruno.com/pricing)

本地保存并不等于所有数据都不会发送出去，请求仍会发往配置的 API。凭据不要写入可提交文件，响应、测试报告和截图也可能含敏感内容。CLI 当前文档说明默认采用 Safe Mode；使用他人提供的 collection 时，先检查请求和脚本，不要随手开启更宽的执行权限。[CLI 安全模式](https://docs.usebruno.com/bru-cli/overview)

## 4 Difftastic：从格式变化里找出关键修改

一次修改可能同时调整函数、更新配置，再经过格式化。普通 diff 中大片换行和缩进变化，会让真正需要确认的参数变得不够醒目。

Difftastic 按语法结构比较文件，支持 Go、Python、JSON、YAML 等类型。它能帮助阅读变化，但不能判断业务行为是否正确。[官方介绍](https://difftastic.wilfred.me.uk/)

### 先做一次性比较

准备两份需要比较的普通配置文件：

```bash
difft before.yaml after.yaml
```

如果想查看当前仓库的未提交改动，可以临时调用它，无需先修改全局 Git 配置：

```bash
git -c diff.external=difft diff
```

例如检查发布配置时，重点确认镜像标签、启动参数、环境变量和资源设置。对于包含模板语法的 Helm 文件，先固定 Helm 版本、release 名称、namespace 等输入，分别渲染要比较的版本，再看输出差异。[Git 集成方式](https://difftastic.wilfred.me.uk/git.html)

看完结构差异，仍可用普通 Git diff 检查完整文本。尤其是文件权限、换行约定和需要生成补丁的场景，不应只保留一种视图。

### 平台、成本与边界

Difftastic 提供 Windows、Linux、macOS 预编译程序，采用 MIT 许可证，免费。比较本地文件无需在线服务，适合在 WSL、开发机或已有云端工作区里使用。[平台与安装](https://difftastic.wilfred.me.uk/installation.html)

它与 VS Code/Git 的差异查看功能重叠，收益主要来自语法展示。无法识别或解析失败时会回退到文本比较；大量变化可能消耗较多时间和内存。输出用于人阅读，不是可直接应用的补丁，也不负责自动合并。[限制说明](https://github.com/Wilfred/difftastic)

特别要区分“没有明显语法变化”和“行为完全相同”。配置含义还取决于应用版本、默认值和运行环境，最终仍需相应检查与测试。

## 5 lnav：把多份日志放到一起看

回归失败后，应用、任务组件和网关可能各有一份日志。分别搜索同一个请求 ID 可以找到片段，却不容易看清它们发生的先后关系。

lnav 是终端日志查看器，能够识别支持的日志格式，把多份记录按时间合并，并提供搜索、过滤和查询。使用已有日志文件即可，不需要先部署日志服务器。[官方介绍](https://lnav.org/)

### 从同一次运行的三份日志开始

```bash
lnav controller.log worker.log gateway.log
```

文件名仅作示例。进入后先确认日期、时区和格式识别是否正确，再搜索相关请求 ID。如果只想显示命中的记录，可以输入：

```text
:filter-in demo-request-001
```

先看最早出现的异常，再放宽过滤查看前后文。只保留错误行可能漏掉前面的重试、取消或依赖失败，所以不要过早认定最后一条异常就是根因。[稳定版命令说明](https://docs.lnav.org/en/stable/commands.html)

需要 Codex 协助时，可以提供相关时间段的脱敏片段，并保留来源、时区和请求关联信息。没有必要先把整个诊断目录上传出去。

### 平台、成本与边界

lnav 采用 BSD-2-Clause，免费。上游 README 已列出 Linux、macOS、Windows 二进制；具体包以对应发行版资产为准。已有 WSL/Linux 终端工作流时，优先在那里使用即可。[官方仓库](https://github.com/tstack/lnav)

本地日志可以离线分析，但自定义格式可能需要补充解析定义。没有时间戳、时区不一致或机器时钟偏移，都会影响时间线；顺序本身也不能证明因果关系。[日志格式说明](https://docs.lnav.org/en/latest/formats.html)

k9s 适合观察集群现场，lnav 适合回看已经收集的多文件日志。它们处理的是不同环节。lnav 不承担集中采集、长期留存和分布式追踪，也不会自动补齐缺失日志。

## 6 先把一个工具用进真实任务

如果从一个开始，优先考虑 just。挑出最近反复查找的检查命令，整理成少量入口，看看下次接续任务时是否更容易确认范围和运行结果。如果已有优秀的 Makefile，就不为换工具而迁移。

之后按当前痛点选择：频繁排查集群就试 k9s，反复拼请求就试 Bruno，配置审查噪声多就试 Difftastic，多文件日志难以关联就试 lnav。每次只接入一个小流程，保留现有工具作为参照。

准备离线使用时，还要把安装包、运行依赖、对应版本说明一起准备好，并在相同操作系统与架构上确认。在线文档可能比稳定发行版更新，复制命令前应先核对实际版本的帮助信息。普通开发工具没必要全部塞进产品安装包；先在允许使用的开发或诊断环境里验证价值，可以少承担一份交付与升级负担。

判断是否值得留下，可以问三个问题：下次还能准确找到入口吗？执行范围和结果更容易核验了吗？省下的重复操作是否多于维护配置的负担？这些答案，比安装数量更能说明工具有没有真正帮上忙。

看 agent 架构图时，经常会遇到一串名词：skills、mcp、tools、subagents、hooks、plugins。

单独查每个词，都能找到解释。但放到一张图里，又容易产生几个问题：

- 已经有工具了，为什么还需要 skill？
- mcp 和工具是一回事吗？
- 多一个 subagent，是不是就多了一个模型？
- 把规则写进文件，ai 就一定会遵守吗？

可以先记住这句话：

> **agent 负责推进任务，tools 负责具体操作，skills 提供做事方法，mcp 负责连接外部能力，subagents 负责分工，hooks 在指定时机触发处理。**

我平时更多使用 codex，下面就用程序员熟悉的一件事，把这些概念串起来：

> 给一个 go 服务增加查询任务状态的 api：`GET /api/tasks/{id}`。沿用现有代码结构和错误格式，补齐测试，先给我看结果，得到授权后再提交推送。

这是一个简化的示例项目，不对应我的真实业务代码。codex 相关说明依据截至 2026 年 10 月 6 日的官方文档整理，具体能力还要看当前入口、版本和环境。

## 先把要做的接口说清楚

假设这个服务已经有任务查询逻辑，我们要增加一个 http 接口，方便调用方查询任务状态。

请求示例：

```http
GET /api/tasks/task-123
```

任务存在时，返回 `200` 和下面的 json：

```json
{
  "id": "task-123",
  "status": "running"
}
```

先约定三个基本场景，避免 codex 自己猜需求：

| 场景 | 预期结果 |
| --- | --- |
| 任务存在 | 返回 200，包含任务 id 和状态 |
| 任务不存在 | 返回 404，沿用项目的错误响应格式 |
| 查询过程出现内部错误 | 返回 500，不把底层错误细节直接交给调用方 |

这些是示例项目的接口约定。实际开发时，要先看已有接口怎样处理错误，再和需求对齐。

接下来，codex 需要读代码、加接口、补测试、检查结果。架构图里的组件，正好分别参与这些工作。

## 先把名词对应到开发工作

可以把 codex 想成一位接到开发任务的同事。他会读代码、修改文件、运行测试，也可以请其他助手分头检查。

| 组件 | 白话理解 | 在增加接口这件事里做什么 |
| --- | --- | --- |
| agent | 负责推进任务的开发同事 | 判断缺什么，安排下一步，检查结果 |
| `AGENTS.md` | 项目的协作约定 | 说明目录、错误格式、测试命令和提交规则 |
| skills | 可复用的开发操作手册 | 提供新增接口的步骤和检查要点 |
| tools | 真正执行操作的工具 | 读写代码、搜索定义、运行测试 |
| mcp | 外部能力的统一连接方式 | 读取已接入需求系统或接口文档中的材料 |
| subagents | 分头工作的助手 | 一个审查错误处理，一个检查测试覆盖 |
| hooks | 在指定时机触发的处理 | 在支持的事件后执行代码检查 |
| plugins | 打包好的扩展套件 | 一起分发开发技能和外部连接能力 |

这些组件不要求全部出现。一个小接口，可能用一个 agent 加几个工具就能完成。

## agent：根据结果继续推进

大语言模型，也就是 llm，负责理解内容、生成代码和提出下一步操作。codex 这样的 agent 应用，还要执行工具、接收结果、管理上下文和控制流程。

例如，模型提出“看看已有 handler 怎么写”，真正打开文件的是环境里的工具。工具返回代码后，模型才能判断路由怎样注册、错误怎样返回。

工作循环可以简化为：

```text
理解接口需求
    ↓
读取现有代码，判断改动位置
    ↓
修改代码和测试
    ↓
运行检查，查看结果
    ├─ 发现问题 → 修正后再检查
    └─ 达到目标 → 交付结果
```

假如测试发现“任务不存在”仍返回 `200`，codex 应该检查错误分支，修正为约定的 `404`，再验证。一次文件写入成功，并不代表接口已经完成。

## AGENTS.md：先知道项目的规矩

我不想每次加接口，都重复说明目录结构、测试命令和协作要求。这些长期约定适合写进仓库根目录的 `AGENTS.md`。

示例：

```markdown
# go 服务约定

- handler 放在 internal/handler/，沿用现有路由和响应结构。
- 新接口尽量复用已有查询逻辑，不引入无关依赖。
- 错误响应沿用现有格式，内部错误不直接暴露给调用方。
- 新接口补齐正常、资源不存在和内部错误的测试。
- 格式化改动的 go 文件，运行相关测试。
- 保留已有修改；未经授权，不提交或推送。
```

codex 会读取适用的项目说明。个人说明和项目说明可以叠加，目录越靠近当前工作目录，越能补充具体约定。它不会无条件把仓库里所有同名文件都读进去。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

三类信息可以这样分工：

```text
AGENTS.md：这个服务的代码结构、错误格式和协作规则
接口开发 skill：怎样增加接口并验证结果
当前请求：增加 GET /api/tasks/{id}
```

说明文件提供背景和要求。真正控制文件访问、网络和操作权限的，还包括运行环境的沙箱与审批机制。

## skills：保存一套可复用的接口开发方法

项目规范告诉 codex“这里有什么约定”，skill 则告诉它“这类任务怎样做”。

在本地 codex 项目中，一种官方支持的组织方式是：

```text
task-service/
├── AGENTS.md
├── .agents/
│   └── skills/
│       └── add-go-api/
│           ├── SKILL.md
│           └── references/
│               └── api-checklist.md
├── go.mod
└── internal/
    └── handler/
```

`SKILL.md` 是核心，参考资料、脚本和模板都是可选的。下面是一个简化示例：

```markdown
---
name: add-go-api
description: 为现有 go 服务增加 http 接口，适用于需要沿用项目结构、处理错误并补齐测试的任务。
---

1. 读取适用的 AGENTS.md、已有路由、handler 和测试。
2. 确认请求、响应和错误场景，不清楚的地方先核对。
3. 复用现有查询逻辑，按项目结构实现接口。
4. 补齐正常、资源不存在和内部错误的测试。
5. 格式化改动文件，运行相关测试，再按项目要求检查。
6. 报告改动、测试结果和未验证项，遵守当前提交授权。
```

这个文件没有重新训练模型。它保存的是完成任务时可以参考的步骤。[官方 skills 文档](https://learn.chatgpt.com/docs/build-skills)。

在 codex cli 或 IDE 扩展中，可以通过 `/skills` 选择技能，或在提示词里用 `$` 指定已发现的技能：

```text
$add-go-api
增加 GET /api/tasks/{id}，沿用已有查询逻辑和错误格式。
补齐 200、404、500 场景的测试，先检查，不提交或推送。
```

也可以只描述任务，让 codex 根据技能简介选择是否使用。文件放进目录以后，仍要确认技能已被发现，适用范围也写得清楚。

### 为什么只按需读取技能

假设我还装了排查日志、数据库迁移、前端开发等技能。增加这个接口时，把所有技能全文都带上，会占用上下文，也容易混入无关要求。

上下文就是模型这次工作时能够参考的材料。skills 采用按需展开的方式：

```text
先看技能名称和简介
    ↓
确认需要接口开发技能
    ↓
读取 add-go-api 的 SKILL.md
    ↓
需要细节时，再看 api-checklist.md
```

这像先看手册目录，再翻相关章节。skill 提供步骤，最终仍要用实际代码和测试检查结果。

## tools：真正读写代码、运行测试

tool 是 agent 可以调用的操作能力。codex 能做什么，取决于当前入口提供了哪些工具，以及环境允许什么操作。

在这个任务里，工具的作用很直接：

```text
读取文件：查看 AGENTS.md、路由、handler 和测试
搜索代码：找到已有任务查询逻辑及其调用方式
编辑文件：增加 handler、注册路由、补齐测试
运行命令：格式化代码，执行 go test
```

例如，codex 可以通过终端工具查看示例项目：

```bash
rg --files internal/handler
git status --short
go test ./internal/handler
```

前两条帮助了解代码位置和已有修改，最后一条运行这个包的测试。如何沿用已有代码、怎样处理失败结果，还需要 agent 判断。

**skill 提供方法，tool 执行操作。** 把“运行测试”写进 skill，不会自动给环境装好 go，也不会保证测试能通过。

## mcp：需要外部材料时才接进来

mcp 是 model context protocol，也就是模型上下文协议。它让应用用统一方式连接外部工具和上下文。

如果需求和代码已经在当前仓库里，直接读取文件就可以。只有当接口约定保存在外部需求系统或文档服务中，才可能需要使用已接入的 mcp：

```text
codex
  ↓
mcp client
  ↓
已接入的需求或文档服务
  ↓
取得接口字段和错误约定
  ↓
回到仓库实现代码
```

mcp 规定怎样交流，tool 是接入后能执行的具体操作。它们可以配合，但不是同一个东西。

在 codex cli 中，可以查看已经配置的服务：

```bash
codex mcp list
```

这不会替我安装服务或授予权限。本地 codex 支持连接本地进程或远端服务；云端能否使用同一服务，需要另外确认网络、连接和认证。[官方 mcp 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)。

例如，能读取需求，不代表能修改需求单，更不代表能推送代码。实际权限由服务和账号决定。

## subagents：把独立审查分给助手

接口实现后，可以明确要求 codex 使用子代理分工：

```text
请用两个子代理检查这次接口改动：

1. 检查错误处理：任务不存在是否返回 404，
   内部查询失败是否返回 500，响应是否沿用项目格式。
2. 检查测试：是否覆盖 200、404、500，
   是否真的验证了响应字段和状态码。

子代理只读代码并返回意见，不修改文件。
等待结果后，由主代理统一修正。
```

这样，每个助手都有明确的任务和输出。主对话不必塞满所有搜索与检查记录，只需要接收发现的问题和对应文件位置。

当前官方文档已经介绍 codex 的子代理工作流。可以直接请求分工，也可以由适用的项目或技能说明提出分工要求。子代理可以有自己的上下文和模型设置，不要求每个助手换一种模型。[官方 subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)。

多代理会增加模型与工具的工作量。小改动通常不必分工；让两个助手同时改同一个 handler，也容易冲突。只读审查、主代理统一修改，更容易整合。

## hooks：在指定时机触发检查

如果只在提示词里写“记得跑测试”，仍可能漏掉。hook 可以在支持的事件发生时，按配置运行处理。

例如，codex 官方文档列出的 `PostToolUse` 是工具执行后的事件，`Stop` 是当前回复结束时的事件。[官方 hooks 文档](https://learn.chatgpt.com/docs/hooks)。

在支持并已配置相应 hook 的环境里，可以设计：

```text
codex 完成目标代码编辑
    ↓
匹配已配置的 hook
    ↓
运行相关检查
    ↓
把失败结果交回 codex 修正
```

这只是流程示意。实际使用要配置匹配范围和处理逻辑，确认目标工具在覆盖范围内，不必每次工具调用都跑全套测试。

对于这个 go 接口，先主动执行格式化和测试往往就够用。假设改动的是以下两个文件：

```bash
gofmt -w internal/handler/task_status.go internal/handler/task_status_test.go
go test ./internal/handler
go test ./...
```

第一条格式化指定文件；后两条分别检查 handler 包和当前模块的包。实际文件名、目录和测试范围应以项目为准。[gofmt 官方说明](https://pkg.go.dev/cmd/gofmt)、[go test 官方说明](https://pkg.go.dev/cmd/go#hdr-Test_packages)。

还可以用 git hook 或 ci 触发检查，它们和 codex 的生命周期 hook 是不同机制。云端任务里，codex 主动检查，再由 ci 检查提交，已经能形成一条实用流程。

测试通过说明被测试的场景符合预期。错误处理是否完整、是否引入不必要的改动，仍需要结合需求审查。

## plugins：把开发配件打包分发

如果接口开发技能和一个需求文档服务经常一起使用，可以打包成 plugin，让其他人安装。

一个假想的接口开发插件可以包含：

```text
接口开发插件
├── add-go-api skill
├── 接口检查清单和模板
└── 读取需求文档所需的 mcp 能力
```

plugin 主要解决分发和安装。增加一个小接口，不必先做插件；仓库里的一个 skill 就能保存方法。

当前官方文档区分了各入口：codex cli 和桌面端有插件入口，IDE 扩展不支持插件。插件可以包含 skills、mcp 能力和 hooks，但云端编排的 chatgpt work 不支持插件 hooks，安装插件也不会自动把脚本部署到执行环境。[官方 plugins 文档](https://learn.chatgpt.com/docs/plugins)。

“插件已安装”“需求系统已连接”“测试命令能运行”，是需要分别确认的状态。

## 本地和云端：在目标环境验证能力

codex 的名字相同，工作位置和可用能力却不一定相同。

| 入口 | 开发这个接口时需要确认什么 |
| --- | --- |
| codex cli | 当前仓库、文件权限、go 环境和已有配置 |
| IDE 扩展 | 编辑器工作区、技能和 mcp 是否可用；不套用插件安装流程 |
| codex cloud | 云端仓库和依赖、测试环境、网络范围与认证 |
| chatgpt work 中的云端执行 | 当前提供的技能与工具；不默认继承本地配置或插件 hooks |

本地项目的 `.agents/skills/` 适合保存项目技能。相关文件放进仓库便于管理，但云端是否发现并加载它，仍要看该入口的技能机制。

官方云端环境说明也强调，任务使用自己的准备环境和文件状态，网络访问有独立设置。[官方云端环境说明](https://learn.chatgpt.com/docs/environments/cloud-environments)。

例如，本机能运行测试、能访问需求服务，不能据此断定云端也可以。应该在目标环境实际读取代码、查询材料和运行命令。环境缺失时说明原因，不把未运行的测试写成通过。

## 把增加接口的全过程走一遍

回到开头的请求，一条清楚的开发流程是：

1. **读规范和代码**：确认环境、分支与已有修改，读取适用的 `AGENTS.md`、路由、handler 和测试。
2. **按需加载技能**：使用接口开发 skill，明确请求、响应以及 200、404、500 的约定。
3. **取得缺少的材料**：先读仓库；外部需求或文档已有接入时，再使用 mcp。
4. **用工具实现接口**：复用已有查询逻辑，增加代码和测试，保持改动范围清楚。
5. **按需请求子代理审查**：分别检查错误处理和测试覆盖，由主代理整合。
6. **格式化并运行测试**：查看实际结果，修正问题，报告未验证项。
7. **按授权提交推送**：只包含相关文件，核对远端提交，并跟进 ci。
8. **按项目流程发布**：如果提交会触发部署，再确认部署结果；没有发布任务时，交付到约定的阶段即可。

子代理、mcp 和 hooks 都可以省略，读取代码和测试也可能反复发生。架构图里的箭头说明配合关系，不是每个任务都必须走完所有组件。

## 遇到问题时，先判断缺什么

| 开发时遇到的问题 | 优先考虑 |
| --- | --- |
| 不知道代码目录、错误格式和测试约定 | 补充 `AGENTS.md` |
| 每次加接口都要重复交代相同步骤 | 整理接口开发 skill |
| 无法读写代码或运行测试 | 确认可用 tool 和执行环境 |
| 需求保存在外部系统 | 使用已接入的 mcp 或连接工具 |
| 错误处理和测试需要独立审查 | 明确请求 subagent 分工 |
| 希望在特定事件后自动检查 | 使用已验证的 hook，或 git hook、ci |
| 希望把技能和连接能力反复安装、分享 | 打包成 plugin |

对这个 go 接口，最基本的流程就是“读规范和代码 → 实现接口 → 补齐测试 → 检查结果”。

`AGENTS.md` 保存项目约定，skill 保存方法，tools 完成操作；需要外部资料、独立审查和自动触发时，再增加 mcp、subagents 和 hooks。看清各自的分工，就更容易理解 agent 怎样把一句开发需求推进成可以审查的代码改动。

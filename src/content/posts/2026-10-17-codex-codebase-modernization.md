## 1 本期要解决什么问题

本期选择《Modernizing your Codebase with Codex》。它适合学习如何组织复杂系统的开发与改造，尤其是怎样把“代码写出来”推进到“行为有证据可验证”。

## 2 原文精读：从一条业务流程开始

文章以 cobol 投资组合系统为例：先选一个有限范围的业务流程，梳理现状，再设计目标实现、编写验证方案，最后对比新旧结果。它用执行计划、现状说明、目标设计和验证说明承接这些工作，让工程师保留对架构与业务规则的判断。[官方原文](https://developers.openai.com/cookbook/examples/codex/code_modernization)

我认为，这篇文章最值得学的是：**给 codex 的任务要同时包含“改什么”和“怎样证明改对了”。**

下面通过一个任务调度系统展开。这个案例和后面的提示词是为本期编写的，并非原文案例。

## 3 先把“复杂系统”变成可以讨论的具体对象

假设你维护一个后台任务平台，大致流程是：

用户提交任务 → api 校验 → 数据库存储 → 调度器分配 → worker 执行 → 回传状态。

现在你希望改善任务查询功能。如果只说：

> 帮我重构任务模块，提高代码质量。

codex 需要自行猜测很多事情：可以改接口吗？可以改状态定义吗？能否调整数据库？是否允许顺便重写调度器？

我建议先把任务收敛成一句话：

> 重构任务状态查询的内部实现，保留现有接口、权限语义和状态映射，只改变这一条查询路径。

这句话给出了可审查的范围。你随后讨论的每项改动，都可以检查它是否服务于这个目标。

第一轮也不必覆盖整个调度系统。选择查询路径作为练习，是因为它仍涉及权限、数据模型和状态一致性，同时便于观察输入与输出。

## 4 先让 codex 解释系统，再决定如何修改

我建议第一轮只读分析，并要求每项结论提供代码依据。可以这样提问：

> 先阅读本项目适用的 AGENTS.md，只读分析“任务状态查询”流程。请找出接口入口、权限判断、状态读取、响应转换和已有测试，说明它们之间的调用关系。关键结论引用具体文件与符号；无法从代码确认的事项标为 UNKNOWN。暂不修改文件。

审阅时，重点看它能否回答这些问题：

| 要弄清楚的问题 | 为什么会影响实现 |
| --- | --- |
| 哪些用户能查询哪些任务？ | 查询成功不能绕过权限边界 |
| 状态来自数据库、缓存还是外部执行器？ | 数据源不同，更新延迟和失败方式也不同 |
| 内部状态怎样映射成对外状态？ | 重构可能无意改变客户端看到的含义 |
| 任务不存在和没有权限，分别返回什么？ | 错误行为也是接口的一部分 |
| 哪些测试覆盖了这条路径？ | 决定哪些既有行为能够直接核验 |

这里有一个很有用的审查动作：**随机挑一条结论，沿着引用回到代码中确认。** 如果引用无法支持结论，应先纠正系统理解，再继续设计。

代码也未必能解释全部业务。例如，“取消中的任务为什么仍显示运行中”，可能来自兼容历史客户端的约定。这类问题需要负责人补充；不能让 codex 用看起来合理的新规则替代它。

## 5 把完成条件写成别人也能检查的事实

“功能正常”“重构完成”都太含糊。我建议在实施前列出一张行为表：

| 场景 | 需要明确的预期 |
| --- | --- |
| 有权限的用户查询自己的任务 | 响应字段及状态含义符合约定 |
| 用户查询他人的任务 | 按既定策略拒绝，且不泄露不应暴露的信息 |
| 查询不存在的任务 | 返回规定的错误行为 |
| 查询执行失败的任务 | 失败状态与错误信息的暴露范围符合约定 |
| worker 刚刚更新状态 | 明确允许的延迟与读取规则 |
| 数据源不可用 | 明确错误返回，而非误报任务成功或不存在 |

表中的答案不能凭空填写。已有系统可以从代码、测试和业务约定中建立基线；新系统则需要先确定需求。

此外，**旧系统的输出不一定都正确。** 如果发现旧行为本身是缺陷，应把“修复缺陷”单独写进范围和预期，避免把有意变化误判为回归，也避免为了追求一致而保留已确认的错误。

## 6 让每轮实现都能被独立验收

下面是我建议的实施顺序：

1. **建立行为基线。** 用有代表性的输入记录当前结果，并补上必要的回归检查。
2. **实施最小改动。** 只处理选定查询路径，不顺带升级依赖或调整其他模块。
3. **运行针对性验证。** 先检查这次改动最容易破坏的行为，再运行受影响范围内的测试。
4. **审阅差异与证据。** 检查代码为何改变、哪些行为得到验证、哪些仍未验证。
5. **处理失败后再继续。** 测试失败时先判断是实现错误、环境问题，还是预期本身需要澄清。

尤其需要警惕“修改测试让它通过”。测试当然可能写错，但改变预期应该有业务依据。否则，绿色结果可能只是把问题藏进了断言。

阶段结束时，可以要求 codex 按这个格式交付：

> 说明改动范围、实际运行的检查及结果、失败与修复情况、尚未验证的事项，并展示本次任务的代码差异。完成结论必须对应预先约定的验收条件。

这样的报告能帮助你判断是否接受这一阶段，也方便后续接手。

## 7 长期项目中，记录应当回答不同的问题

下面是我的项目组织建议，不是必须采用的文件清单：

| 信息 | 应回答的问题 |
| --- | --- |
| 项目规则 | 如何工作、遵守哪些约束？ |
| 系统说明 | 当前系统如何运行，依据在哪里？ |
| 阶段计划 | 这次准备改变什么，完成标准是什么？ |
| 验证记录 | 实际做了什么检查，观察到了什么？ |

已有相应文档时直接使用，避免为每种信息再建一个文件。

`AGENTS.md` 有官方发现规则；普通计划文件则需要明确引用。特别是，不能假定把说明放进任意目录后 codex 都会自动读取。当前文档说明，项目指令的发现沿项目根目录到当前工作目录的路径进行。[AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

对于较长任务，我建议每次结束至少留下三项内容：当前有效决策、已经取得的验证证据、下一项尚未完成的工作。下一次继续前再对照实际代码检查，避免旧记录被当成当前事实。

## 8 阅读这篇教程时，需要保留的边界

原文主要面向既有系统现代化。将它用于从零开发复杂系统时，我建议把“新旧行为对比”转换成“实现与需求、接口契约的对比”。

原文也明确说明，示例中的模块仍是初稿，尚需连接运行入口。因此，照着生成相似文件并不代表已经得到可运行系统。[原文的示例限制](https://developers.openai.com/cookbook/examples/codex/code_modernization)

它引用的 `PLANS.md` 教程目前已归档，官方提示可能涉及过时模型或 api。可以学习其规划思想，具体工具操作应对照当前文档。[归档提示](https://developers.openai.com/cookbook/articles/codex_exec_plans)

本期没有实际运行教程示例，也没有验证你的任何项目；上面的任务调度案例属于教学设计。原文及版本提示核实于 2026 年 10 月 17 日。

## 本期小练习：用 20 分钟检查一条真实业务路径

在一个你有权读取的项目里，选择一个查询接口，让 codex 完成一次只读分析。可以直接使用这一段：

> 阅读项目适用的 AGENTS.md，选择一个范围有限的查询接口，只读分析其入口、权限、数据来源、主要业务规则、错误处理和现有测试。请用具体代码位置支撑结论，列出三个以上值得核验的边界场景，并说明哪些行为目前缺少证据。最后提出一个最小改进方案及验收标准。不要修改文件、访问外部环境或执行写入操作。

练习验收标准：

- 你能沿着它的引用找到真实实现。
- 你能说明哪些结论已确认、哪些仍待确认。
- 方案范围足够具体，你能明确接受或拒绝。
- 完成标准可以通过检查或测试验证。

先完成这一次分析。它会帮助你判断：在让 codex 承担更大的实现任务前，你们是否已经对系统行为建立了共同理解。

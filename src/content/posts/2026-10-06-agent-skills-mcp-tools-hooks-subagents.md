看 agent 架构图时，经常会遇到一串名词：skills、mcp、tools、subagents、hooks、plugins。

单独查每个词，都能找到解释。但放到一张图里，又容易产生几个问题：

- 已经有工具了，为什么还需要 skill？
- mcp 和工具是一回事吗？
- 多一个 subagent，是不是就多了一个模型？
- 把规则写进文件，ai 就一定会遵守吗？

可以先记住这句话：

> **agent 负责推进任务，tools 负责具体操作，skills 提供做事方法，mcp 负责标准化连接，subagents 负责分工，hooks 在指定时机触发处理。**

本文用同一个例子把它们串起来：

> 帮我写一篇介绍 redis 缓存的博客。参考已有文章的风格，用简单例子解释，最后保存到博客的文章目录。

本文使用 Claude Code 的文件名举例，例如 `CLAUDE.md` 和 `.claude/skills/`。这些是具体产品的约定，其他 agent 工具的目录、加载方式和支持范围可能不同。

## 先把这些名词翻译成人话

可以把 agent 想成一位接到任务的编辑。他会查资料、动笔、检查，也可能请同事帮忙。

| 组件 | 白话理解 | 在写博客这件事里做什么 |
| --- | --- | --- |
| agent | 负责把事情做完的编辑 | 判断还缺什么，安排下一步，检查结果 |
| tools | 编辑手里的工具 | 搜索网页、读取文章、保存文件 |
| skills | 可反复使用的操作手册 | 规定如何选例子、组织文章、核对事实 |
| mcp | 统一的连接方式 | 让助手通过标准接口访问 GitHub 等系统 |
| subagents | 分头工作的助手 | 一个查资料，一个检查概念是否准确 |
| hooks | 到了指定时机就触发的处理 | 文件写入后运行格式检查 |
| 项目说明文件 | 项目的注意事项 | 说明文章目录、文件名和写作约定 |
| plugins | 打包好的扩展套件 | 把一组技能、助手和相关配置一起安装 |

这些组件不要求全部出现。只写一篇很短的文章，可能一个 agent 加几个工具就足够了。

## agent 怎样把一句话变成一件完成的事

大语言模型，也就是 llm，负责理解内容、生成文字和提出下一步操作。agent 应用还要负责执行工具、接收结果、管理上下文和控制流程。

例如，模型提出“读取这三篇旧文章”，真正打开文件的是运行环境里的读取工具；工具返回文章后，模型才能继续判断风格。

一个典型的工作循环可以简化为：

```text
接收任务和上下文
      ↓
判断下一步需要做什么
      ↓
调用工具执行操作
      ↓
查看结果，检查是否达到目标
      ├─ 还缺资料或发现错误 → 继续处理
      └─ 已达到目标 → 交付结果
```

在博客例子里，agent 可能先读旧文章，再查 redis 官方文档。写完后发现某段把“缓存过期”和“内存淘汰”混在一起，就需要回去核对并修改。

因此，工具执行成功只是一个中间结果。文件成功保存了，还要检查内容、位置和格式是否正确。Anthropic 对 agent 的解释也强调，模型会根据过程中的反馈动态选择步骤和工具，而不是只能走预先写死的路线。[参见 agent 的基本模式](https://www.anthropic.com/engineering/building-effective-agents)。

## tools：把想法落实成具体操作

tool 就是 agent 可以调用的操作接口，例如：

```text
搜索网页
读取文件
列出目录
调用某个服务的 api
写入文件
运行检查命令
```

在博客任务里，它们对应的操作很具体：

```text
读取工具：打开三篇旧博客
网页工具：获取 redis 官方文档
写入工具：保存新的 Markdown 文件
命令工具：运行博客项目已有的检查
```

工具只负责自己那一步。读取工具返回文章内容，不会自动判断哪种写法适合初学者；写入工具保存了一篇文章，也不能证明文章里的概念都正确。

可以这样记：**tool 解决“具体怎么动手”，agent 负责决定“现在该动哪只手”。**

## mcp：让不同系统用同一种方式接进来

mcp 的全称是 Model Context Protocol，也就是模型上下文协议。它为 ai 应用连接外部系统提供了一套开放标准。[mcp 官方介绍](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)。

假设旧文章保存在 GitHub。接入支持 GitHub 的 mcp server 后，agent 应用可以通过它提供的接口读取仓库文件。

简化后的关系是：

```text
agent 应用
    ↓
内置的 mcp client
    ↓
mcp server
    ↓
GitHub 等系统
```

这里的 server 指一个提供能力的程序，可以运行在本机，也可以运行在远端。它不一定是一台单独购买的服务器。

mcp 和 tool 的关系，类似“接口规范”和“接入后能使用的功能”：

- mcp 规定客户端和服务端怎样交流；
- tool 是能够执行的具体操作，例如“读取某个仓库文件”；
- mcp server 还可以提供资源和提示模板，不只提供工具。[参见 mcp 架构](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)。

本地文件读取工具完全可以由 agent 应用直接提供，不必绕一遍 mcp。一个任务是否需要 mcp，取决于数据和能力在哪里，以及应用支持哪种接入方式。

连接成功以后，也只能使用账号和服务实际允许的功能。接入 GitHub，并不意味着自动获得所有仓库的写权限。

## skills：把反复讲的话写成操作手册

给 agent 一套工具，它可能已经能完成任务，但每次完成的方式未必一致。

今天写博客时，它先解释概念；明天又可能直接堆缩写。于是我们经常要重复补充要求：

```text
面向初学者。
先说这个技术解决什么问题。
用一个例子贯穿全文。
说明适用条件和容易误解的地方。
核对官方资料，再保存文件。
```

skill 就适合保存这类可以复用的做事方法。按 Agent Skills 规范，一个 skill 至少包含 `SKILL.md`，还可以带脚本、参考资料和模板。[Agent Skills 格式规范](https://agentskills.io/specification)。

例如，一个写作技能可以组织成这样：

```text
write-tech-blog/
├── SKILL.md
├── references/
│   └── writing-guide.md
├── assets/
│   └── post-template.md
└── scripts/
    └── check-frontmatter.py
```

下面是一个简化的 `SKILL.md` 示例：

```markdown
---
name: write-tech-blog
description: 根据技术主题或资料撰写面向初学者的中文博客，包含例子、事实核对和格式检查。
---

1. 读取现有博客，确认文章格式和表达方式。
2. 用一句话说明主题解决什么问题。
3. 选一个简单例子，贯穿主要概念。
4. 用官方资料核对容易混淆的说法。
5. 按文章模板保存，并检查文件内容。
```

这里没有重新训练模型，也没有修改模型参数。我们提供的是模型执行任务时可以读取和使用的材料。

### 为什么不一次把所有 skill 都读进去

假设助手有写博客、做表格、分析日志、检查代码等几十种技能。写博客时把所有技能全文都带上，会占用上下文，还会混进很多无关内容。

上下文可以理解为模型本次处理时能够参考的材料，它有容量限制。

skills 常用的办法叫 progressive disclosure，可以简单理解为“按需展开”：

```text
先看名称和简介
      ↓
发现当前任务需要写博客
      ↓
读取写作 skill 的详细步骤
      ↓
需要模板或检查脚本时，再使用对应文件
```

这很像查一本手册：先看目录，再翻相关章节，需要细节时才查附录。Anthropic 的 skills 设计正是用这种方式逐步提供材料。[skills 的工作方式](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)。

在 Claude Code 中，也可以直接调用某个 skill，而不完全依赖模型自动选择。具体调用方式和自动加载规则由产品决定。[Claude Code 的 skills 文档](https://code.claude.com/docs/en/skills)。

所以，skill 能提高复用性和一致性，但仍需要用实际任务检验：有没有选对技能、有没有照着做、结果是否合格。

## 项目说明文件：告诉助手这里的规矩

skill 讲“这类任务怎么做”，项目说明文件讲“这个项目有什么约定”。

以 `CLAUDE.md` 为例，博客项目里可以写：

```text
文章保存在 src/content/posts/。
文件名使用日期和英文主题。
文章开头需要 title、description、pubDatetime、tags。
写作时先解释用途，再展开术语。
```

文章开头这块标题、日期、标签等元信息，通常叫 frontmatter。

这样，助手进入项目后就有机会直接读到这些背景，不必每次都重新询问。实际加载范围与文件位置有关，子目录中的说明也可能按需加载。[Claude Code 的项目说明机制](https://code.claude.com/docs/en/memory)。

可以按下面的方式分配内容：

```text
项目说明：文章目录在哪里，采用什么格式
写作 skill：如何把复杂概念解释清楚
当前请求：这次写 redis 缓存
```

但说明文件本质上仍是给模型看的上下文。涉及删除文件、发布内容或访问敏感数据时，还要依靠实际权限、沙箱和审批机制控制风险，不能只靠一句“请不要这么做”。

## subagents：把独立的小任务交给助手

文章比较复杂时，一个 agent 可以把部分工作交出去：

```text
主 agent：负责文章结构和最终整合
    ├─ 资料助手：查官方文档，返回关键事实和来源
    └─ 审稿助手：检查概念、例子和前后矛盾
```

subagent 可以理解为被委派任务的助手。在 Claude Code 的实现中，它有自己的上下文，可以配置工具访问范围等；使用什么模型也可以配置，不一定要换成另一种模型。[subagents 官方文档](https://code.claude.com/docs/en/sub-agents)。

它带来的一个直接好处，是主对话不必塞满全部搜索结果。资料助手可以读很多页面，只把相关结论和来源交回来。

不过，分工必须讲清楚。下面两种任务描述，效果通常会差很多：

```text
含糊的安排：去研究一下 redis。

清楚的安排：核对 redis 的过期删除与内存淘汰有什么区别，
返回各自的触发条件、一个简单例子和官方来源。
```

还要避免两个助手同时修改同一段文章。一个写正文，另一个只返回审稿意见，会更容易整合。

多助手也有成本：它们需要各自处理信息，主 agent 还要协调和复核。任务很小时，分工带来的等待和重复阅读可能比收益更大。

## hooks：在指定时机触发处理

假设每次保存博客后都要检查文章头部字段。如果只在提示词里写“记得检查”，仍然可能漏掉。

hook 提供了另一种触发方式：在系统支持的事件发生时，按配置运行处理逻辑。

例如：

| 时机 | 可以安排的处理 |
| --- | --- |
| 工具执行前 | 检查这次操作是否符合限制 |
| 工具成功执行后 | 记录结果，或对新文件执行检查 |
| 助手结束当前回复时 | 检查是否还有未处理的问题 |

在 Claude Code 中，`PreToolUse`、`PostToolUse`、`Stop` 就是这类事件的例子。不同事件能做什么，要看各自的规则。[hooks 参考文档](https://code.claude.com/docs/en/hooks)。

博客场景可以这样理解：

```text
agent 写入文章
      ↓
匹配到已配置的写入后事件
      ↓
运行 frontmatter 检查
      ↓
发现缺少 description
      ↓
把问题交回 agent 修正
```

这段是流程示意，真正使用时还要配置事件、匹配范围和检查程序。

一些介绍会把 hooks 简写成“确定性自动化”。更准确地说，**触发时机由事件和配置控制；处理结果是否确定，还要看执行了什么。**

运行固定字段检查脚本，规则可以很明确；让模型判断“这篇文章是否易懂”，仍然会包含模型判断。Claude Code 也提供基于提示词或 agent 的 hook，不能把所有 hook 都当成固定脚本。

## plugins：把一套配件打包交付

当写作 skill、资料助手、检查 hook 和 mcp 配置经常一起使用时，逐个配置会比较麻烦。

plugin 可以把相关组件打包成一个安装单元。以 Claude Code 为例，插件可以包含 skills、agents、hooks 和 mcp servers 等组件。[plugins 官方介绍](https://code.claude.com/docs/en/plugins)。

一个假想的博客插件可能包含：

```text
博客插件
├── 写作 skill
├── 审稿 subagent
├── 格式检查 hook
└── 读取内容源所需的 mcp 配置
```

安装这样的套件，主要是省去重复配置。它不代表里面一定有一个新模型，也不代表每项组件都必须存在。

插件可能包含可执行代码，安装前需要检查来源和权限。不能因为名字叫“写作插件”，就默认它只会处理文章。

## 把写博客的全过程走一遍

现在回到开头的请求：写一篇介绍 redis 缓存的博客，并保存到文章目录。

一种合理的配合方式是：

1. **读项目说明**：确认目录、文件名和文章头部格式。
2. **加载写作 skill**：明确先解释问题，再用例子展开的写法。
3. **调用工具收集材料**：读旧文章、打开官方文档；如果文章在远端系统，可以通过已有的 mcp 接入读取。
4. **按需要分工**：把资料核对交给 subagent，主 agent 整理提纲。
5. **生成正文**：用一个商品详情页的缓存例子解释数据怎样读写。
6. **写入文件**：调用工具把文章保存到目标目录。
7. **执行检查**：由已配置的 hook 或 agent 主动调用检查程序，确认格式。
8. **回看结果**：检查概念、来源和保存位置，修正问题，再交付。

其中，第 3 步可能反复发生，第 4 步可以省略，第 7 步也不一定要通过 hook 完成。

架构图里的箭头主要是在说明配合关系，不能理解为每次都必须从左到右把所有组件走一遍。

## 什么时候该用哪一个

遇到问题时，可以先判断到底缺什么：

| 遇到的问题 | 优先考虑 |
| --- | --- |
| 每次都要重复交代同一套步骤 | 把方法整理成 skill |
| 不知道当前项目的目录和约定 | 补充项目说明文件 |
| 根本没有读文件、查网页等操作能力 | 提供合适的 tool |
| 需要接入一个外部系统 | 看是否有合适的 mcp server 或其他接口 |
| 独立的小任务很多，主对话材料太杂 | 使用 subagent 分工 |
| 某个检查必须在特定事件发生时执行 | 配置 hook，并验证是否覆盖目标场景 |
| 希望把一组扩展反复安装或分享 | 打包成 plugin |

刚开始不需要一次装齐。先让“读取材料 → 完成任务 → 检查结果”这条最短流程可靠运行，再根据实际问题补组件。

如果助手没有读到资料，增加再多写作 skill 也补不上事实；如果只是文件格式总出错，一个小检查程序可能就够了。

## 总结

再看这类 agent 架构图，可以把它拆成几个很普通的问题：

```text
谁推进任务？           agent
靠什么执行操作？       tools
参考什么做事方法？     skills
怎样连接外部系统？     mcp
能把哪些工作交出去？   subagents
何时自动触发处理？     hooks
项目有什么约定？       项目说明文件
怎样一起安装和分享？   plugins
```

理解这些组件，关键是看清它们各自补上了哪一部分能力。方法、工具、连接、分工和检查配合好了，agent 才更容易把一句需求变成可核对、可交付的结果。

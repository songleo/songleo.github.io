“帮我从零写一个离线安装器。”

把这句话交给 ai，它可能很快创建目录、编写脚本，再告诉你已经支持镜像导入和应用部署。但回过头来看，几个问题可能还没有答案：到底支持什么环境？缺一个文件时怎么办？同一个安装包重复执行会发生什么？所有进程退出了，就算安装成功吗？

代码已经出现，完成标准却还不清楚。继续往下做，每个人都可能按自己的理解补齐空白，最后得到一个看起来功能很多、实际难以判断是否符合需求的程序。

这篇文章从这个问题开始，介绍 sdd，也就是规格驱动开发。我们用一个正在规划的离线安装器作为背景，挑出“制作前检查输入配置”这一小块，完整走过需求、设计、任务、实现指导和验收。

案例经过通用化处理。文中的字段、命令和测试名称是教学约定，示例结果是预期行为；它们不代表某个现有安装器已经实现或验证。你不需要准备真实集群，也不需要先安装一套 sdd 工具，准备一个练习目录和能编辑文本的工具就可以开始。

## 1. sdd 是什么，解决什么问题

sdd 是 spec-driven development 的缩写，可以译为“规格驱动开发”。在本文采用的实践方式里，我们先把预期行为写成可审阅、可验证的规格，再用它指导设计、任务拆分、实现和验收；发现新情况时，继续维护这些约定。

这里的“规格”可以理解成一份双方都能核对的说明。例如，“配置错误时要友好提示”还比较模糊；“缺少产品源码提交时，指出缺失字段，以非零退出码结束，并且不启动构建”就更容易判断有没有做到。

[github spec kit 的方法说明](https://github.com/github/spec-kit/blob/main/spec-driven.md)强调由规格驱动实现，并在开发中持续细化规格。本文采用的是一个便于初学者练习的小步流程，不把任何工具的模板或命令当作唯一标准。

对离线安装器来说，sdd 主要帮助我们提前处理这些分歧：

| 容易出现的问题 | 把它写进规格后的变化 |
| --- | --- |
| “支持集群安装”各有各的理解 | 明确节点角色、架构、版本和操作范围 |
| ai 自动补上升级、清理和回滚 | 写出本期非目标，让额外功能先成为待讨论项 |
| 缺材料时临时下载另一个版本 | 明确材料身份和失败行为，避免静默替换 |
| 正常路径能跑，异常路径靠猜 | 在实现前就列出缺失、错误、中断等场景 |
| 做完后只说“测试通过” | 每条验收标准对应具体检查和结果 |

这些收益来自持续使用规格。文档如果生成后就不再审阅、不参与验收，同样会逐渐失效。sdd 也不能保证 ai 不犯错，更不能替代实际运行和人的判断。

### 什么情况下值得用

如果工作涉及多个组件、多人交接、反复迭代，或者操作错误的代价较大，提前明确约定通常值得。安装器就很典型：制作包、校验材料、检查环境和部署应用之间存在依赖，前一步的假设会影响后面很多动作。

如果只是修改一句提示文案，需求和验收可能两句话就够。没必要为了使用 sdd，强行创建几十页文档。对于尚不清楚是否可行的问题，也可以先做范围受控的探索，再把结论写进规格。

## 2. 需求、设计、任务和证据分别写什么

先记住这四个问题：要做什么？怎么做？本次做哪一小块？拿什么证明做到了？

| 产物 | 回答的问题 | 安装器中的例子 |
| --- | --- | --- |
| `spec.md` | 谁需要什么行为，什么情况下算通过 | 缺少源码提交时拒绝继续制作 |
| `design.md` | 用什么结构实现这些行为 | 先解析配置，再校验字段，最后由入口返回结果 |
| `tasks.md` | 具体实施顺序和完成条件 | 实现字段检查、接入命令入口、验证成功与失败场景 |
| 测试与验收记录 | 当前实现是否符合约定 | 缺字段样例被拒绝，且外部执行器没有被调用 |

文件名并非 sdd 的强制要求。例如，[kiro 的规格文档](https://kiro.dev/docs/specs/)使用 `requirements.md`、`design.md` 和 `tasks.md` 组织需求、设计与任务。本文使用 `spec.md`，只是为了让练习中的叫法保持一致。

需求和设计也不是完全没有交集。如果产品明确要求运行在 linux/amd64 上，这就是需求约束；至于校验模块用哪个函数、选哪种解析库，通常属于设计。判断方法是：换一种实现方式后，这条要求是否仍然必须成立？

对于这次练习，可以先使用下面的目录。测试和证据目录在真正开始实施后再添加，不需要先填满所有文件：

```text
installer-lab/
├── spec.md
├── design.md
├── tasks.md
├── examples/
├── tests/
└── evidence/
```

把这些文件纳入版本管理，能帮助我们查看需求为何改变、哪次实现对应哪版约定。提交和发布仍按项目流程处理，生成文档并不自动意味着可以推送或部署。

## 3. 先为安装器画出边界

在拆功能之前，先说明用户和使用场景。这个案例有三种角色：制作者负责组装离线包，实施者负责安装，审阅者负责核对输入、过程和结果。

先给整个项目定一个方向，再选很小的一部分练习：

| 项目问题 | 本例的范围 |
| --- | --- |
| 最终想解决什么 | 将明确来源的材料制作成可校验的离线包，再在指定环境中安装 |
| 第一版面向什么环境 | 已有 kubernetes 集群；linux/amd64 单主节点，应用组件只部署到主节点 |
| 第一版暂不做什么 | 集群搭建、升级、卸载、自动回滚和多主节点部署 |
| 本次练习做什么 | 检查制作配置中的源码提交和目标架构 |
| 本次练习不证明什么 | 不证明源码可取得、镜像可构建、材料齐全或真实安装成功 |

单主节点和 amd64 都是这个案例的项目选择，不是 sdd 的要求。完整安装器还需要固定版本、组件清单、材料锁、文件摘要等信息，本次练习只覆盖输入检查的一小部分。

可以先把下面这段话交给 ai：

```text
我们要练习用规格驱动开发实现一个离线安装器。
请先阅读已有项目说明，整理用户、目标、输入输出、约束和非目标。

本轮只讨论制作配置检查，不获取材料、不构建镜像、不连接集群。
把已确认事实、建议和待确认问题分开。
只询问会影响范围或行为的问题，先不要写业务代码。
```

你需要亲自审阅的是这些行为是否符合目标，而不只是句子写得是否通顺。例如，“配置有问题就自动修复”听起来方便，但可能改掉制作者原本想用的版本。是否允许这种行为，应该明确决定。

## 4. 把“检查配置”写成可以验收的规格

先写一个故意不够好的版本：

> 支持检查构建配置，保证输入正确、安全、可靠。

问题在于，“正确”“安全”“可靠”还没有对应到具体输入和可观察结果。我们可以继续追问：检查哪些字段？字段缺失和空字符串一样处理吗？错误时只警告还是停止？检查通过后会不会直接开始构建？

### 先写用户需求，再写验收标准

本例的用户需求可以写成：

> 作为离线包制作者，我希望在启动制作前发现配置缺失或不受支持的值，以便先修正输入，避免带着错误配置进入后续操作。

接着为这次小练习确定六条验收标准。下面使用 `AC-L01` 等教学编号，与实际项目中的需求编号分开。

| 编号 | 给定条件与操作 | 预期结果 |
| --- | --- | --- |
| `AC-L01` | 读取一份制作配置 | 顶层必须是对象，且恰好包含 `source_commit` 和 `architecture` 两个字段；缺失、重复或未知字段被拒绝 |
| `AC-L02` | 检查 `source_commit` | 值必须是由 40 个小写十六进制字符组成的字符串；空值、错误类型、短提交和分支名被拒绝 |
| `AC-L03` | 检查 `architecture` | 值必须是字符串 `amd64`；其他值和缺失值被拒绝 |
| `AC-L04` | 文件不可读取、不能解析或字段不合格 | 以非零退出码结束，给出字段或文件层级的原因，不直接回显整份输入 |
| `AC-L05` | 配置满足上述规则 | 报告“静态配置检查通过”并以零退出码结束；不声明已经完成构建或安装 |
| `AC-L06` | 执行此次检查，无论结果如何 | 不修改输入，不访问网络，不读取真实源码仓库，不启动构建或部署 |

这里的 40 位提交格式是为了让练习具体，假定样例产品仓库使用 git 的 sha-1 对象格式；它不代表所有 git 仓库都使用同一种对象格式。正式项目需要根据实际源码合同决定规则。

同样，未知字段是否拒绝、大小写是否接受，都是需要决定的行为。本文选择严格校验，帮助初学者理解确定的输入边界；这些选择不会自动成为其他项目的需求。

### 用例子检查自己是否说清楚了

在设计阶段选择 json 后，可以把这份内容保存为 `examples/valid.json`：

```json
{
  "source_commit": "0123456789abcdef0123456789abcdef01234567",
  "architecture": "amd64"
}
```

这串提交值是虚构的，只用于格式练习。校验通过并不证明它在任何仓库里存在。

再准备一份缺少源码提交的 `examples/missing-commit.json`：

```json
{
  "architecture": "amd64"
}
```

以及一份包含合法十六进制短提交的 `examples/short-commit.json`：

```json
{
  "source_commit": "0123456",
  "architecture": "amd64"
}
```

第二份样例应该因为缺字段失败，第三份应该因为长度不足失败。再补一个架构为 `arm64` 的样例，就能检查程序有没有擅自放行本次不支持的架构。

**正例和反例应该围绕需求设计。** 如果测试只检查函数是不是返回了某个对象，却没有验证缺字段时是否阻止后续动作，就还没有覆盖真正关心的行为。

可以让 ai 帮忙审查规格：

```text
请审阅 AC-L01 到 AC-L06。
逐条指出是否存在歧义、冲突、无法观察的描述或遗漏的失败场景。
为每条标准给出至少一个验证办法。

不要把建议直接写成已确认需求，也不要开始实现。
如果只是实现细节，留到设计阶段讨论。
```

当本轮涉及的行为已经清楚，就可以进入设计。其他尚未解决的问题可以保留，但要写明是否阻塞当前任务：源码访问权限可以留到真实构建前确认；是否允许缺字段继续，则会阻塞本次校验功能。

## 5. 从规格走到设计、任务和验收

一轮实践可以按下面的顺序推进。任何一步发现前提不成立，都可以带着证据回到前面修正。

```text
选一条需求 → 澄清行为 → 写验收标准 → 确认本轮范围
                                      ↓
记录结果 ← 对照验收 ← 小步实现 ← 审阅设计并拆任务
    │
    └── 发现问题或新需求 → 调整相关约定 → 下一轮
```

### 5.1 写一份够用的设计

本例选择 json 文件和一个命令行校验入口。采用 json 的理由很简单：字段少，练习阶段不需要复杂配置语法。正式项目也可以选择其他格式，但不能在没有讨论的情况下改变已约定的行为。

`design.md` 可以先写下面这些内容：

| 设计项 | 本例的决定 |
| --- | --- |
| 输入 | 用户明确指定的本地 json 文件 |
| 解析 | 检查文件可读性、语法和重复键；解析结果必须是对象 |
| 校验 | 检查字段集合、类型、提交格式和架构，不自动补默认值或改写输入 |
| 成功输出 | 标准输出给出简短通过信息，退出码为 `0` |
| 失败输出 | 标准错误给出原因，退出码为 `2`；多个问题可以只报告第一个 |
| 外部操作 | 校验入口不依赖网络、源码仓库、构建器或集群客户端 |
| 验证方法 | 正常与错误样例、入口退出码检查、输入前后比对、外部操作未发生检查 |

其中，非零表示失败来自规格；具体选择 `2`、错误写到哪个输出通道，是本例在设计中确定的接口约定。

重复键值得单独关注：如果输入中出现两个 `architecture`，不能依赖解析器随意留下其中一个。设计必须明确如何发现并拒绝它，后面的测试也要对应覆盖。

下面是拟定的命令形式，**需要在练习项目实现后才能运行**：

```text
installer-lab config-check examples/valid.json
```

还没有实现时，不要把这段命令写进“已可使用”的操作手册。先把它当作待实现接口审阅即可。

可以这样给 ai 分配设计工作：

```text
基于已确认的 AC-L01 到 AC-L06，提出最小设计。
说明输入格式、解析顺序、错误输出、退出码、外部依赖和验证办法。
每项设计应能对应到需求；额外选择请说明理由。

不要实现镜像构建、下载或部署。
先让我审阅设计，再拆分本轮任务。
```

### 5.2 把任务拆到可以独立检查

任务“完成配置模块”仍然太大。可以拆成下面三个，最后一起构成从命令入口到可观察结果的小闭环：

| 任务 | 实施内容 | 完成条件 |
| --- | --- | --- |
| `T-L01` | 实现解析和字段校验 | 正常、缺失、重复、未知字段、错误类型和错误值均按规格处理 |
| `T-L02` | 接入命令行入口 | 输出与退出码符合设计，检查不会触发制作动作 |
| `T-L03` | 补齐行为验证并记录结果 | 每条验收标准都有对应证据，未执行项有原因 |

`T-L02` 依赖 `T-L01`，完整验收依赖两者。测试场景可以提前整理，不必等代码写完才思考。

要注意：“创建了测试文件”不是任务完成条件。真正的完成条件应该说明测试验证了什么，以及执行结果是什么。

### 5.3 一次只实施确认过的部分

在真实练习中，确认规格和设计后，可以使用下面的提示词。写教程本身不需要同时实现这段程序。

```text
请实施已确认的 T-L01 和 T-L02，并完成 T-L03 的必要验证。
以当前版本 spec.md 和 design.md 为依据，保留已有修改。

只实现制作配置检查，不获取材料、不构建镜像、不连接集群。
在项目约定的 Linux 环境运行测试。
发现规格矛盾或必须新增的行为时，先指出影响，不自行放宽条件。

完成后展示差异，逐条报告 AC-L01 到 AC-L06 的证据、结果和未完成项。
不要把未执行的测试记为通过，不继续实施其他功能。
```

ai 可以帮助写代码和准备验证，但它给出的完成说明仍然需要审阅。尤其要检查：有没有为了让测试通过而删掉失败场景、把严格校验改成警告，或者在没有需求依据的情况下扩大功能。

### 5.4 用验收矩阵判断是否完成

可以在 `evidence/config-check.md` 中记录结果。下面是**尚未执行的记录模板**，不是一次测试报告：

| 场景 | 对应标准 | 要观察的结果 | 当前状态 |
| --- | --- | --- | --- |
| 有效配置 | `AC-L01`、`AC-L02`、`AC-L03`、`AC-L05` | 静态检查通过，退出码 `0` | `NOT_RUN` |
| 缺字段、重复字段或未知字段 | `AC-L01`、`AC-L04` | 分别拒绝并解释原因，退出码 `2` | `NOT_RUN` |
| 空值、错误类型、短提交或分支名 | `AC-L02`、`AC-L04` | 分别拒绝，指出源码提交字段问题 | `NOT_RUN` |
| 不支持的架构 | `AC-L03`、`AC-L04` | 拒绝，不自动改成支持的值 | `NOT_RUN` |
| 文件缺失或 json 损坏 | `AC-L04` | 文件或解析错误，不回显整个输入 | `NOT_RUN` |
| 正常与失败路径的副作用检查 | `AC-L06` | 输入未改动；网络、源码访问、构建和部署调用均为零 | `NOT_RUN` |

实际执行时，把表中成组的场景展开成独立用例。记录代码版本、测试命令、运行环境、执行结果和证据位置，失败时附上原因。

对于“没有启动构建”，不能只凭日志中没出现“构建”两个字就下结论。可以让外部执行入口由记录调用次数的替身接管，一旦被调用就使测试失败；同时审查校验路径是否存在绕过替身的外部操作。替身就是可控制的测试对象，不需要真的构建镜像。

当后续把校验器接入真实制作流程时，还要补一条集成验证：配置被拒绝后，制作流程确实停止。单独校验器正确，并不能证明它的调用者一定正确使用了结果。

### 5.5 分清这次到底证明了什么

| 证据层级 | 能支持的结论 | 还不能支持的结论 |
| --- | --- | --- |
| 规格审阅 | 本轮约定清楚，未决项有处理方式 | 功能已经实现 |
| 本地样例与自动化测试 | 配置检查在已覆盖场景下符合要求 | 真实源码和材料可以取得 |
| 真实构建与独立验包 | 指定输入可以产出并校验指定包 | 包可以在所有环境安装 |
| 指定环境的安装验证 | 指定包在该环境完成了约定检查 | 所有业务场景和发布条件都满足 |

本轮结束时，准确的结论应该类似“配置检查的六条教学标准已有对应结果”。完整安装器的材料锁、来源校验、制作流程和安装流程仍需要后续任务。

## 6. 人和 ai 分别负责什么

使用 ai 时，最容易忽略的是：它能生成一份看起来完整的回答，但缺失的业务前提可能仍然没有得到解决。

| 环节 | ai 可以帮助做什么 | 人需要重点判断什么 |
| --- | --- | --- |
| 需求 | 整理场景、提出遗漏和矛盾 | 谁使用、真正需要什么、哪些行为可接受 |
| 设计 | 比较方案、说明依赖和代价 | 选择是否适合当前范围，假设是否有依据 |
| 实施 | 编写代码和必要测试 | 差异是否符合约定，是否引入额外行为 |
| 验收 | 运行检查、归纳证据和缺口 | 证据是否支持结论，是否满足进入下一阶段的条件 |

普通的小实现选择可以在已授权范围内处理，不需要每写一个函数都重新确认。需要停下来讨论的是改变目标、扩大范围、改变对外行为，或者缺少关键依据的问题。

如果发现“仓库里没有提供完整材料锁”，可以记录为 `UNKNOWN`，再写清楚由谁提供、怎样核实、在哪一步之前必须解决。不能拿虚构摘要填进去，再把样例成功当成真实组包成功。

也不用把所有上下文都重复粘贴给 ai。把稳定约定保存在项目文档中，每轮明确当前需求编号、任务范围和完成条件，通常更容易检查有没有跑偏。

## 7. 需求改变后，怎样继续实践

假设完成配置检查后，制作者提出新需求：

> 制作前还要检查所有必需材料是否已经在本地；如果不齐，列出缺口并停止，不自动联网补齐。

这时不要只在代码里加几个判断。先明确“必需材料”由哪份清单定义、怎样识别文件，以及只检查存在性是否足够。文件存在和摘要正确是两件事，需要分别约定。

一次受控的变化可以这样推进：

1. 在规格中新增材料预检需求，写出齐全、缺失、摘要错误的预期行为。
2. 确认范围变化：原来的配置检查禁止访问外部材料；新功能允许读取哪些本地路径，是否另设入口。
3. 在设计中补充材料清单、读取边界和错误报告，不顺便加入下载功能。
4. 拆分实现与测试任务，关联到新的验收标准。
5. 实施后验证新增场景，并回归会受到影响的旧行为。
6. 更新证据和状态；旧测试结果保留对应的旧版本，不冒充本次验证。

如果发现的只是代码错误，例如规格要求拒绝未知字段而实现漏检，应修复实现并补验证。如果规格本身有歧义，则先澄清行为。不要为了迁就当前代码，把失败的验收标准删掉。

可以使用这样的变更提示词：

```text
新增需求：制作前检查本地必需材料，缺失或摘要不符时停止，不自动下载。
请先分析它对现有规格、设计、任务和测试的影响。
列出保持不变的行为、必须新增的约定和需要确认的问题。
给出最小修改方案，确认后再实施；不要直接改代码。
```

sdd 的文档会随着认识变化而更新。一次确认表示当前阶段有可执行的依据，不意味着以后不能改变。

## 8. 第一次实践可以怎样开始

第一次不必挑战完整离线安装。就用本文的配置检查，做完一轮：

1. 创建独立练习目录，写下用户、目标和本轮非目标。
2. 阅读六条教学验收标准，用自己的话解释每条要观察什么。
3. 准备一份有效配置和几份无效配置，检查你是否能在运行前判断预期结果。
4. 写最小设计，明确输入、输出、退出码和禁止发生的动作。
5. 拆出三个任务；确认本轮约定后，再让 ai 实现。
6. 查看差异、运行必要验证，按矩阵填写真实结果。
7. 提出一个小变更，练习同步更新规格、设计、任务和测试。

做的过程中，可以用下面的表检查是否出现偏差：

| 常见错误 | 更稳妥的处理 |
| --- | --- |
| 把 sdd 理解成先生成三份很长的文档 | 先写足以支撑本次小功能的约定，并实际用于验收 |
| 一开始就设计整个安装器的全部扩展 | 保留整体方向，先做一个能从入口走到结果的小闭环 |
| 把 ai 提出的建议当成业务事实 | 标明建议、依据和待确认问题 |
| 只检查正常输入 | 根据需求补充缺失、错误和不应发生的操作 |
| 测试只是复述当前实现 | 从验收标准独立推导预期行为，允许测试揭露实现错误 |
| 文档和代码不一致时只改其中一个 | 判断是需求变化还是实现缺陷，再同步相关内容 |
| 把示例通过写成真实安装成功 | 按输入、环境和验证层级限定结论 |

如果你能解释“这条需求为什么存在、这个设计如何满足它、这个任务做完后拿什么证明”，就已经有了继续实践的基础。下一轮再把同样的方法用到材料校验、离线包制作和安装阶段管理，逐步扩展安装器。
